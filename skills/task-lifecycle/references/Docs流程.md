# Docs流程

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：用户明确以 README/SDK/API 文档/现有文档站点/内部维护手册为受管主目标时。

**唯一主责**：DOC01～DOC10 的完整独立 Docs 工作流；文档与实际 API/使用者体验一致

**直接消费者**：Docs DOC01～DOC10、Docs Site Gate、正式审查、实际示例与受众。

**联动 Reference**：`Docs受众与站点质量.md`、`产物内容与自审契约.md`、`验证与证据分流.md`。

## 适用时逐项执行

1. DOC01 准确读者（初次使用者、SDK 集成、维护者、内部）/公开级别/预期任务；纯只读审查只启用安全辅助而非自动改文件。
2. DOC02 只读对照实际源码、包、CLI/API、当前 README/docs/site/nav/链接，形成可核查 inventory；无法读的对象单独标未验证。
3. DOC03 先定义读者首个可成功任务、信息架构、导航和 Required/Conditional；不得为编写文档新增不存在的产品能力。
4. DOC04 明确真实允许修改的文档/导航/示例/站点、依赖和验证权限；DOC05 只在授权范围写交付文档，内部审批日志留仓库外。
5. DOC06 计划获准后专业核对真实读者与事实，生成可核对 Finding；DOC07 运行真实浏览器/链接/示例/必要构建与读者任务证据，`build passed` 不等于任务完成。
6. DOC08 只有真正需要和有许可时发布/迁移；DOC09 记录当前交付、各受众验证范围及维护交接；DOC10 任意阶段插入变更，重新判断消费者/旧证据/审批失效。
7. 仅 README 且无站点的任务，G-DOC 站点特定步骤按 `N/A+reason`，**不得自动新建网站**。Docs 发现产品 Bug/新 API 时形成单独受管候选，不能未经批准改业务实现。
8. 文档的使用说明只承诺经证实的安装/接口/兼容性；示例、历史页或模型猜测不能替代真实消费者。

## 必须拒绝的反例

- 内部 Task/审查日志进入公开 Quick Start；纯 README 修订自动生成站点；没有浏览器仍声称“用户成功”；为了让文档示例正确而偷改源码；把构建成功当作 SDK 正常调用。



## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 5.1 统一阶段协议

每个固定主阶段都必须能回答下面八个问题，具体执行子步骤由项目事实决定：

1. **Enter**：当前任务/上游真实文件身份、确认/授权、现场与前置依赖是否有效？
2. **Role**：主视角、消费者、反向质量视角是什么？分别检查什么？
3. **Plan**：生成该阶段动态子步骤、适用正式产物、验证方式、分解与回退条件。
4. **Generate**：按 Required/Conditional/Optional 生成或更新正式产物；不适用项写理由。
5. **SelfReview**：阅读有效上游和真实项目事实，执行缺漏/反向证据审查；可自主修订至收敛，文件内留下自审摘要。
6. **FormalReviewIfRequired**：专项审查须先有绑定当前对象版本的计划且按模式有效验收，然后按计划执行 Finding 闭环；普通自审不递归新建专项计划。
7. **Approval**：Confirm 逐件真实人工确认；Auto 仅授权内且证据充分的中间产物 `auto-accepted`；报告事实认可不等于对象通过。
8. **Exit/Recovery**：更新阶段证据、合法退出、下一个动作，变更时进入插入式 A10/B10/DOC10；失败时局部阻断和返工，不损害无关工作。

这是 Skill 应引导的**人可读流程协议**，不是系统级无法绕过的事务状态机。退出条件不具备时，宿主可能仍允许用户直接调用工具；插件不可宣称可以全局阻止该行为。

### 5.4 Docs DOC01～DOC10：阶段输入、产物和关键退出

| 阶段 | 阶段目的与输入 | 必需结果/适用审查 | 退出与返回 |
|---|---|---|---|

| DOC03 内容与信息架构 | DOC01/02 有效读者及事实 | 文档内容契约、公开/维护/内部边界、导航、读者任务与成功标准 | 不为改善文档自行创造产品 API |

| DOC07 真实消费者验证 | 当前页面、API 示例和站点预览 | docs build、真实浏览器导航/链接/用户任务/适用辅助验证器 | `build passed` ≠ `用户能完成任务`；必要 E4 不可测时阻断相应交付 |

### 5.5 阶段错误、停止与复原

**已确认变更传播的具体执行协议（R5 受控细化，依据 REQ-008/009/069/073～075）**：出现任务目标、公开契约、技术决策、受影响代码/测试或正式产物的**实质变化**时，受影响操作暂停，创建独立且可读的《变更影响分析.md》（普通未发生实质变化的咨询无需强造），至少记录：真实变更来源及决定、Task/版本/Hash 与适用确认来源、变更前后真实差异、原始 REQ/UC、直接/间接依赖（正式产物→Work Item→源码→真实消费者→测试/Docs/`.http`→交付/发布）、仍有效和需失效的审查/批准/测试、受影响的 A/B/DOC 阶段、允许/禁止操作与恢复条件、应修订文件/版本及独立质量门禁、必要正反回归。对未证实的消费者/传播链标记 `unverified`，不能只凭编号或已存在一份计划声称全链核对。确认记录必须实际绑定本次获批范围，`fast` 可用简洁表格而不省略此有条件必需的变更记录。

**判断和退出**：无真实影响的既有证据可基于明确理由复用；被改变的对象及其关键消费者必须重新核实与按当前合法模式批准。涉及新的产品取舍或公开行为时保留 `suggested-unapproved` 并请真人决定，不把旧 Auto、旧 Hash 或报告事实认可当作新批准。必须确保影响列表反向扫描实际 diff/生成源/打包集合，才能恢复受影响任务链。V1 使用 Markdown 与宿主现有工具，不新增变更传播服务或自动强制拦截。

| 事件 | 应走的技术处置 |
|---|---|
| 重要需求或授权缺失 | 只停止依赖该约束的正式写入/验收，列出需用户决定的精确事项 |
| 当前阶段必需产物未审/未确认 | 退回该产物的有效审查/审批，不绕过门禁 |
| 上游已确认版本实质变化 | 触发 A10/B10/DOC10，评估连带证据失效及可能需要再确认 |
| 外部工具结果未知/写入部分成功 | 先读真实现场、Git dirty、日志，不盲目再次执行 |
| 已存在批准范围内实现错误 | 定位最小修复和回归，不要求重启全部生命周期 |
| “建议更好”但不在已批准范围 | 标为 `suggested-unapproved`，不进入实施任务或测试通过标准 |
| 产品性不可决定 | 给用户理由、优缺点、替代（含保持现状）和精确影响，等待真人决定 |
