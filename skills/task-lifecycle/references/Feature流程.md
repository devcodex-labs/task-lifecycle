# Feature流程

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：确认任务类型 Feature，或 Bugfix/Docs 获授权转 Feature，并进入/恢复对应 A 阶段时。

**唯一主责**：A01～A10 全部固定阶段与阶段退出；实施计划/代码/发布必须依实际授权和已批准使用契约

**直接消费者**：Feature A01～A10、正式审查、授权、验证、交接；根据 API/Docs/并行风险按需加载其他 Reference。

**联动 Reference**：`产物内容与自审契约.md`、`确认授权与变更.md`、`验证与证据分流.md`，高风险参见 `正式专项审查与Finding.md`。

## 适用时逐项执行

1. 00 有效后依次围绕 A01 需求评审（提议与现有行为隔离）、A02 使用契约（用户如何安装/配置/调用/错误/边界）、A03 技术方案（不得反改 UC）、A04 实施计划（工作项依赖/质量门禁）、A05 授权代码与专业审查、A06 真实验证、A07 可交付文档与受影响消费者、A08 有条件发布、A09 真实完成/交接执行。
2. A10 是**任意阶段发现目标/契约/源码/消费者/权限实质变化时插入**的影响分析回路，暂停仅受影响节点；不要求 A09 之后机械运行 A10。
3. 每个 A 阶段先明确实际输入事实、Required/Conditional/Optional 的产物适用性与专业角色，建立动态子步骤、核验器、依赖和完成条件，再在合法权限内实施；正式产物需文件级自审，专项审查必须有获批准的准确计划。
4. A02 的对外 API 字段按实际存在的契约逐项核对 type/domain/必填/默认/null/错误/权限/兼容/消费者，不虚构 REST/SDK；A03 的技术方案不得用工程方便更改用户批准的行为。
5. A05 每批先回读有效需求/UC、实际 Git dirty 与消费者；执行后检查 diff→需求和需求→代码两个方向、必要回归。A06 仅真实执行的测试可标 passed，权限不足需保留阻断。
6. A07 分离公开使用说明与内部过程报告；有实际站点且适用时调用 Docs Site Gate；API `.http` 按 off/suggest/generate 独立授权处理。
7. A08 无发布意图/权限则 `N/A+reason`；A09 不伪称实际用户终验，只有证据与当前版本适配的交付可声明完成。

## 必须拒绝的反例

- A02 不存在实际 API 却编造“必填 REST”；A03 未经用户决定改公开默认值；A05 擅自优化未批性能目标；A06 未运行仍 passed；A08 自动 Git push；A10 当作必跑的最后一步；fast 跳过已触发的专项审查。



## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 5.1 统一阶段协议

每个固定主阶段都必须能回答下面八个问题，具体执行子步骤由项目事实决定：

1. **Enter**：当前任务/上游真实文件身份、确认/授权、现场与前置依赖是否有效？
2. **Role**：主视角、消费者、反向质量视角是什么？分别检查什么？
3. **Plan**：生成该阶段动态子步骤、适用正式产物、验证方式、分解与回退条件。
4. **Generate**：按 Required/Conditional/Optional 生成或更新正式产物；不适用项写理由。
5. **SelfReview**：阅读有效上游和真实项目事实，执行缺漏/反向证据审查；可自主修订至收敛，文件内留下自审摘要。
6. **FormalReviewIfRequired**：专项审查须先有绑定当前对象版本的计划且按模式有效验收，然后按计划执行 Finding 闭环；普通自审不递归新建专项计划。
7. **Approval**：Confirm 逐件真实人工确认；Auto 仅授权内且证据充分的中间产物 `auto-accepted`；报告事实认可不等于对象通过。
8. **Exit/Recovery**：更新阶段证据、合法退出、下一个动作，变更时进入插入式 A10/B10/DOC10；失败时局部阻断和返工，不损害无关工作。

这是 Skill 应引导的**人可读流程协议**，不是系统级无法绕过的事务状态机。退出条件不具备时，宿主可能仍允许用户直接调用工具；插件不可宣称可以全局阻止该行为。

### 5.2 Feature A01～A10：阶段输入、产物和关键退出

| 阶段 | 阶段目的与输入 | 必需结果/适用专项审查 | 退出与返回 |
|---|---|---|---|
| A01 需求评审 | 00 任务已合法绑定，目标与边界有效 | 需求评审方案→按模式验收→审查报告→实际 Finding 修订→有效《已确认需求》；建议隔离 | 不留未决产品取舍或 P0/P1 关键阻断；否则停 A01 |
| A02 使用契约 | 需求基线、当前产品调用表面 | 使用契约设计方案、公开安装/输入/输出/异常/示例、契约审查计划和报告，最终有效契约 | 用户使用路径可验收；错误则返 A01/本阶段 |
| A03 技术方案 | 当前有效需求、使用契约、实际源码/依赖 | 完整技术方案、真实关键选择、接口和失败/恢复、技术审查计划及报告 | 方案能实施且有验证路线；硬冲突返 A02/A01 |
| A04 实施规划 | 已确认技术设计、项目现实/依赖 | Work Item/批次/变更范围/角色与风险/验证及 `.http` 适用性、实施计划及专项审查 | 批次可执行且禁止建议已过滤；否则返上游 |
| A05 开发与代码审查 | 有效批次范围与已授权写入 | 实际代码 diff、必要测试、开发记录、实施前后双向需求核查和代码专项审查 | 测试/代码 Findings 关闭，未经批准的 diff 被隔离；否则局部重做 |
| A06 真实验证 | 当前整合代码、冻结验证方案 | D/A/I/H 适用实测及证据、条件性 `.http`、失败回归；验证报告 | 必需声明有通过证据；无法测保留阻断，不得“全绿”掩盖缺漏 |
| A07 交付/用户验收资格 | 实测通过代码和契约版本一致 | 公共使用文档/示例、条件性 Docs Site Quality Gate、交付审查与人类终验条件 | 技术就绪与真实用户终验分离 |
| A08 发布（适用时） | 用户确有发布要求和独立宿主授权 | 版本/包/发布/回滚记录，确认真实发布结果 | 不适用写 `N/A + reason`；未授权停实际发布 |
| A09 完成与反馈 | 所有必需阶段的证据、产品目标与实际消费者 | 完成报告、真实交付、未验证风险、建议/进化候选资格与交接 | 不冒充人工终验，终结任务级 Auto |
| A10 中途变更（插入式） | 任一时刻上游、范围、代码现场、用户目标发生变化 | 影响分析、受影响方案/契约/验证重审、新有效批准 | 仅恢复合法节点，不静默复用旧版本 |

A01/A02/A03 的**设计方案→正式专项审查计划→正式报告→最终对象确认**责任独立；在简单任务中可合并非必需辅助文件，但不得把正式使用契约或完整技术方案跳过。可选 `.http` 文件、文档站点的行为仍按用户在 §12 的既定策略。

### 5.5 阶段错误、停止与复原

**已确认变更传播的具体执行协议（R5 受控细化，依据 REQ-008/009/069/073～075）**：出现任务目标、公开契约、技术决策、受影响代码/测试或正式产物的**实质变化**时，受影响操作暂停，创建独立且可读的《变更影响分析.md》（普通未发生实质变化的咨询无需强造），至少记录：真实变更来源及决定、Task/版本/Hash 与适用确认来源、变更前后真实差异、原始 REQ/UC、直接/间接依赖（正式产物→Work Item→源码→真实消费者→测试/Docs/`.http`→交付/发布）、仍有效和需失效的审查/批准/测试、受影响的 A/B/DOC 阶段、允许/禁止操作与恢复条件、应修订文件/版本及独立质量门禁、必要正反回归。对未证实的消费者/传播链标记 `unverified`，不能只凭编号或已存在一份计划声称全链核对。确认记录必须实际绑定本次获批范围，`fast` 可用简洁表格而不省略此有条件必需的变更记录。

**判断和退出**：无真实影响的既有证据可基于明确理由复用；被改变的对象及其关键消费者必须重新核实与按当前合法模式批准。涉及新的产品取舍或公开行为时保留 `suggested-unapproved` 并请真人决定，不把旧 Auto、旧 Hash 或报告事实认可当作新批准。必须确保影响列表反向扫描实际 diff/生成源/打包集合，才能恢复受影响任务链。V1 使用 Markdown 与宿主现有工具，不新增变更传播服务或自动强制拦截。

| 事件 | 应走的技术处置 |
|---|---|
| 重要需求或授权缺失 | 只停止依赖该约束的正式写入/验收，列出需用户决定的精确事项 |
| 当前阶段必需产物未审/未确认 | 退回该产物的有效审查/审批，不绕过门禁 |
| 上游已确认版本实质变化 | 触发 A10/B10/DOC10，评估连带证据失效及可能需要再确认 |
| 外部工具结果未知/写入部分成功 | 先读真实现场、Git dirty、日志，不盲目再次执行 |
| 已存在批准范围内实现错误 | 定位最小修复和回归，不要求重启全部生命周期 |
| “建议更好”但不在已批准范围 | 标为 `suggested-unapproved`，不进入实施任务或测试通过标准 |
| 产品性不可决定 | 给用户理由、优缺点、替代（含保持现状）和精确影响，等待真人决定 |

### 5.6 三条主流程的深度投影与不可裁剪质量义务

流程深度**不定义第四条主流程**，仅作用在 `00` 和每个适用 A/B/DOC 阶段的动态子步骤、辅助记录和审查深度。必须在工作流方案中记录：`phaseId / status(required|conditional|N/A+reason) / depth / roles / requiredArtifacts / optionalArtifacts / mandatoryGates / verifiers / evidence / nextAction`，可由现有 Markdown 表承载，不新增机器状态文件。

| 任务 | 选档影响 | 不可省略项/反例 |
|---|---|---|
| README 修复错误链接（Docs fast） | 允许将目标/计划/修订/实测记录精简组织，不生成空的 API/数据库方案 | 真实链接或对应导航验证、自审、适用确认；无站点不新建站点 |
| 非公开的小 Bug（Bugfix fast） | 允许精简与修复无关的辅助设计，已有方案可复用时回查有效性 | 修复前故障/假设、最小代码差异、代码审查与必要回归，不伪造“已复现” |
| 支付 API 修改默认值（Feature fast） | 保留简短展示的用户选择，但风险门禁提升到必须项 | 逐字段公开契约、消费者、错误/兼容、资金/权限风险与真实测试，无法通过不能放行 |
| 复杂 Docs 站点结构调整（Docs thorough） | 由事实触发信息架构、真实用户任务及可访问性/站点验证扩展 | 不自动部署/新建站点，读者角色模拟不能冒充真实浏览器或用户实验 |

**批准合同不受深度影响**：原 A01/A02/A03、Bugfix 根因/验证、Docs 读者/站点与各正式专项审查等已触发的独立决策责任仍需适用审批；只有真实不适用或已有确认原件仍合法可复用时才可缩减文件数量。A10/B10/DOC10 为任意阶段插入的变更路由，不可因 fast 禁用。
