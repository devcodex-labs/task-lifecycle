# 任务拆分并行与整合

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：每个受管阶段或独立工作项先读取下述计划执行规则，包括小型只读探查；拆分、并行及整合条款只在存在相应依赖、冲突、派发或汇合事实时适用。

**唯一主责**：阶段/独立工作项的适度计划与动作执行关系；条件触发的动态WorkItem DAG、并行资格与根任务整合责任

**直接消费者**：主Skill、00与三主流程阶段、受管只读探查、工作流/实施计划；条件性多子任务整合与PoC-I。

**联动 Reference**：`确认授权与变更.md` 为人批唯一责任；`验证与证据分流.md` 为整合后质量依据。

## 阶段与独立工作项的计划执行

每阶段或独立工作项在动作前有与规模相称的有效计划，能够回答目标/依据、前置条件、步骤顺序、预期结果、验证与完成条件、停止/调整条件。信息可在现有任务/工作流/实施计划中组合表达；小型只读调查可用简短可见步骤，不要求六个固定槽位、新文件或原生Plan API。事实不足时先安排目的、路径范围和停止条件明确的有界只读探查，再据实际结果细化。

每个实际动作对应当前有效步骤；先核工具真实返回、文件/现场及必要失败出口，再推进依赖该结果的步骤，不把计划中的预期成功当事实。稳定计划和授权复用，不因工具调用、报告或批次重复批准；计划本身不授予写入、网络或发布权限。新事实推翻目标、前提、共享接口或预期结果时，先更新受影响依据、步骤与验证范围，按既有变更/确认协议处理；暂停依赖该变化的动作，其他独立合法工作可继续。

**短例（虚构，未执行）**：先只读核验两份配置是否指向同一共享接口，再决定后续调用验证；第二份配置不可读时结果为未知，不宣称接口一致或执行依赖该结论的调用。接口确有变化则先调整相关步骤，独立文档核对可继续。

## 适用时逐项执行

1. 先用已批准任务/实施计划定义最小依赖 DAG、每项输入/输出、读写与副作用、共同消费者、质量/权限与真实独立性；简单任务不为并行生成假子Agent。
2. 对每项/对子实际决定四态 `parallel-eligible / parallel-analysis-only / serial-required / blocked`，考虑依赖、共享 schema、dirty、真实支持/隔离、收益和协调成本；
   - 仅收益不足或协调成本不划算时记为 `serial-required` 的**原因**，不得另造 `parallel-not-beneficial` 状态。
   - 只读调查符合授权与实际能力时可选择 `parallel-analysis-only`，不可由此推导并行写权限。
**个人项目分支默认禁令（AC-077 / PAC-67 / SC-105）**：无真实用户对本项目及目标操作的明确授权，**不得为个人项目自动创建功能分支、切换当前分支或自动创建 worktree**；
- 也不得清理、重置、覆盖用户的 dirty/staged/untracked/ignored 文件。
- 需要并行隔离时先核实实际 Git/worktree、共享读写集与宿主可用能力：如果不允许新分支/worktree，则只有原任务仍合法且无共享冲突时可选 `serial-required`；
- 若没有任何安全可执行路径则选 `blocked` 并说明阻断，不得强行为追求并行创建分支。
- **拒收反例**：用户只授权分析或源文件修复，模型为“提高效率”自行执行 `git switch -c feature/...`、`git worktree add`、`git reset --hard` 或清理未提交内容；
- **正例**：保留原分支和 dirty，选择合法只读分析或串行，并在确需隔离写入时单独请求授权。

3. `parallel-eligible` 只是资格，实际宿主没有获授权的 spawn/wait/cancel 与独立结果时 `executionEvidence=parallel-not-verified`；可合法的串行回退要留真实记录，`blocked` 不等于自动可串行。
4. 主任务唯一负责正式过程文件当前版、真实用户批准与整体交付；子任务只提交被授权范围内候选 diff/局部证据，不自行批准根任务对象，不能继承无限Auto权限。
5. 接收子任务结果前重新读取当前需求/源码、检查迟到取消/版本失效、共享写冲突、真实 diff 与消费者；合法整合后执行必要整体回归，局部green不代表全局完成。
**暂停/取消/迟到的执行出口（REQ-063）**：根任务范围、上游契约或用户暂停发生实质变化时，立即冻结受影响依赖链及其候选；
- 对**当前宿主实际提供、当前权限允许**且仍运行的子任务尝试 `cancel`，记录请求与实际返回（失败/结果未知也如实留证），并检查是否已产生文件、进程或外部副作用。取消不等于撤销副作用，更不能假定迟到结果安全；
- 重复、取消后返回或版本失效的结果隔离并由根任务重新核对，未知外部动作不得盲重试。
- 其他不依赖该决定且仍有合法授权的子任务可继续，不能把局部暂停升级为全局取消或自动批准。
6. 成本对比只能引用真实可比的时间/成本/失败记录；无客观样本标 not-comparable，不能宣传“并行更快”。

## 长任务容量自适应分批（有序串行也适用，非必须并行）

**触发**：当前已批准任务的对象数、复合子条件、外部依赖、剩余上下文或已实测质量，使一次可靠完成存在漏项/丢失证据的明显风险；无需等用户主动要求“分批”。简单任务直接记录 `no split + reason`，不制造批次。分批不产生新流程、工作流深度档或额外产品能力，亦不默认要求并行代理。

1. 根任务先冻结 `TaskID / 批准范围 / 来源版本SHA / 目标消费者 / 模式与权限 / 完成定义 / 未授权操作`，动态估计各项复杂度和可用上下文/工具预算。
   - 按**稳定来源及依赖边界**划出有穷批次（`BatchID/源ID集合/子条件/前置/实际输入SHA/预期证据/验收门槛/阻断出口`），不要求固定“每批50条”；可在显式理由下重新分批，但要保持完整、不重、不漏的来源全集和追踪关系。
2. 有效同一用户授权/审批计划内自动连续处理安全批次：各批真实读取当下规则与来源、逐条件判定正反例/失败出口、产出可追溯裁决；待修缺陷可归并根因并在获准范围内修订未生效候选，随后复审。不得将自动证据检索、路径命中、批次汇总、同一模型口头说“完成”标为 `covered-by-design` 或 E4 `passed`。较难的批次应缩小粒度或单列明确缺口，不可通过降低质量要求强行收敛。
3. **批次断点（仅有真实合法写权时持久化）**：在仓库外安全过程记录更新 `BatchID / sourceSetHash / targetSHA / 已完成源+子条件ID / 逐项E3裁决及证据路径+Hash / 未裁决+实际原因 / open Findings / E4状态 / nextBatch / 执行时间与可信审批来源`。
   - 原件和已签证据保持只读；每批写后回读，修改规则或候选时受影响证据必须失效并重核。
   - 中断或压缩时不能只按旧摘要、进度百分比或“Auto已启动”续执行任何有副作用动作。
4. **完成门禁**：根任务校验批准的全部源身份与子条件集合 `planned = adjudicated + explicitly-blocked`（无遗漏、无重复），每个裁决须有当前版本的实际规则消费者、正反例、失败出口、证据等级、准确未覆盖条件；
   - `needs-evidence`/`partially-covered` 是明确未收敛事项，不能算设计验收通过。
   - 所有需要修复的 Finding 经批准范围内修订、受影响复审及相应验证后，才可宣称 E3 收敛；E4 真实执行和发布/安装/账户更新另走各自权限门禁。
5. **审批最小化与容量限制**：批次完成、生成临时记录或发现普通 Finding 本身不是新的人批对象；同一有效计划内继续下一批，不得每批请示。若新产品取舍、当前有效计划失效、新源码/环境副作用或高风险外部行为出现，只暂停相关依赖，向用户集中询问确切受保护决定。宿主结束本次调用、上下文/时间/工具硬限制时保存真实进度并明确说明无法继续，不能假称后台自运行或主动恢复。

**正反例**：同一已批准的 1,440 条 E3 任务因一次处理不可靠，自动分为20个相互可追踪批次，连续完成逐子条件裁决并最终汇总有效证据，这是合规做法；若每批仅生成一个待审台账、下轮再要求用户“确认继续”，或完成10批后直接宣称余下10批自动通过，均必须拒收。若某个批次涉及未经授权的真实 Codex 安装，暂停该动作，其他已批准的纯静态批次仍可继续。

## 外部编码执行器委派（默认关闭，约定收窄）

**触发**：A04/B03/DOC04 已批准计划拟把工作项交给宿主外部编码执行器（命令行编码代理，如 `grok`），或预检查发现约定中有本节配置时。
不按宿主名判断：同一台机器上多个宿主都可能看到同一执行器，“命令存在”既不等于“当前宿主是某产品”，也不等于已启用。

1. **默认关闭**：只有《项目约定.md》或《工作区约定.md》（`文件目录版本与跨会话恢复.md` §9.1.1）的「外部执行器委派」节同时满足
   `schemaVersion: 1`、`enabled: true`、`生效确认` 指向真实用户原话来源时才可能启用；
   - 缺失、不可读、未知版本、字段无效或缺生效确认 → 整体 disabled，记 `delegation-config-invalid` 与原因，主会话自己做。
   - 当前用户本次指令只能再收窄（如“这次不委派”），不能放宽约定；约定只按类别配置，不提供逐阶段覆盖。
2. **类别与上限**：`categories` 把四类工作映射到执行器 id 或 `none`，未列出即 `none`；下表是上限，配置只能收窄：

| 类别 | 可交阶段与子步骤（上限） |
|---|---|
| `implementation` | A05 实现已批准 WI 的代码与测试；B04 实现已批准最小修复并补失败→修复测试；DOC05 按已批准内容契约和修改清单编写 |
| `readonly-investigation` | A01 现有行为事实；A02 实际调用表面盘点；A03 依赖版本与源码结构核对；A10/B10/DOC10 受影响面收集；B01 环境/日志/消费者；DOC02 事实盘点 |
| `test-run` | A05 开工基线检查（既有测试/lint/类型检查）；A06 按冻结验证方案运行并交回原始输出；B02 编写并运行复现脚本；B06 原 Bug 与回归测试；DOC07 docs build/链接/`check-docs` 等脚本 |
| `drafting` | A07 按已生效契约起草使用文档与示例；B07 按已定修复起草文档与契约同步文本 |

   - **永不委派**：00、A04、A08、A09、B03、B05、B08、B09、DOC01、DOC03、DOC04、DOC06、DOC08、DOC09 全部内容；
     以及任何阶段的 SelfReview/FormalReview/Approval、Finding 关闭、E1～E4 判定与证据签署、根因与回归结论、整合、commit/push/发布/删除、最终验收。
   - 映射到不可委派阶段或子步骤的配置忽略，并在预检查第 6 项警告；同一 WI 只派一个执行器。
   - 配置启用了某类别也不等于批准某个 WI：仍须 A04/B03/DOC04 已批准计划逐 WI 写明“委派给哪个执行器”。
3. **能力探测（每次派工前）**：命令存在；`--version` 可读；登录有效（以一次无副作用调用的真实返回为准）；当前任务对目标路径已有写入授权（只读类别免此项）。
   任一不满足 → 该类别降级为主会话执行，记 `executor-unavailable` 与实际输出，不阻断其他合法工作。
4. **调用约束**：无界面单次调用、结构化（JSON）输出、`maxTurns` 上限、工作目录限定为目标仓库；
   - 沙箱须限制**读取**范围（如 `grok --sandbox strict`，试跑实测拒读工作目录外的 home 路径，临时目录等其他路径未逐一实测）；只限写不限读的档（如 `workspace`、`read-only`，试跑实测可读工作目录外文件）不得单独使用。
   - 网络关闭是硬规则（禁用网页工具，子进程断网）；子进程断网未实测前记 `unverified`，不得声称已断网；确需网络时由当前用户本次指令单独开启。
   - `deny` 清单覆盖工作目录内及临时目录中的敏感路径（如 `**/.env*`、`*.pem`、凭据文件）；deny 须在只读试跑中实测拦截后，`implementation` 才可启用。
   - 禁止免确认/绕权模式（如 `--always-approve`、`bypassPermissions`）、禁止 commit/push/发布/删除、禁止自建分支或 worktree（如 `-w`），写入只用限定路径的显式许可；
   - 无界面写入许可方式须在试跑中实测“目标路径可写、越界被拒”后，`implementation` 才可启用（首次试跑中 `acceptEdits` 下新建文件仍被拒，属未解决）。
5. **结果回收**：执行器只交候选 diff 与局部证据（同本文件第 4、5 条）；
   - 以结构化输出的停止原因判断是否完成，**退出码 0 不代表完成**（取消或被拒权限也可能返回 0）；未完成按部分结果处理。
   - 主会话回读真实 diff、核对写入范围与越界文件、复跑必要回归，再按原阶段审查和整合；只读调查结果同样由主会话复核。
   - 执行器输出不是用户消息或批准，自报“测试通过”只是线索；执行器审自己写的内容或执行器之间互审均标非独立（`角色与专业审查.md`）。
   - 失败、超时、取消后迟到结果按本文件“暂停/取消/迟到的执行出口”处理，未知外部动作不盲目重试。
6. **留痕**（仓库外任务记录）：约定文件路径与 sha256、生效来源、类别、执行器 id 与版本、完整命令、会话 ID、停止原因、原始输出、diff sha、用量；
   无可比样本时成本与速度记 `not-comparable`。

**正反例（情境，未实测）**：约定缺失时 Codex 与 Grok Bot 都由主会话实现 B04，记 `delegation-config-invalid`，合规；
约定只开 `implementation`，A04 计划写明 WI-2 交 `grok-build`，探测通过、且写入许可方式已按第 4 条实测可用后，以读取受限沙箱、断网和限定路径写入许可调用，主会话复核 diff 后进入 A05 代码审查，合规。
拒收：看到 `grok` 命令就自动委派；用 `--always-approve` 换取无人值守；把执行器的“已审查通过”当 B05 结论；退出码 0 即宣称完成；配置写 `B05: grok-build` 后照做。

## 必须拒绝的反例

- 只要有三个任务就强行派3Agent；把只读调查误标 `parallel-eligible` 并获得写权限；把“收益不明显”记录成第五状态 `parallel-not-beneficial`；两个任务修改同一Schema且无隔离仍并行；blocked事项直接串行跳批准；候选子任务文字“完成”即当整合通过；取消后迟到变更自动应用；无真实计时却声称提效50%。



## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 11.1 资格与成本模型（不是独立 Agent 调度器）

**Work Item 有向依赖与共享契约判定**：每个非平凡拆分在当前《任务工作流方案》/《实施计划》中标注稳定 ID、父任务及获批需求/UC 来源、输入版本、前置 Work Item、预期具体交付物、验收与失败条件、读写/消费者集合、共享接口/Schema 的确认状态。
- 仅对已存在的实际依赖形成有向边；
- 在提交执行方案前检查悬空前置、循环依赖（遇环停止错误节点并重划依赖）、父子目标与原批准范围不一致、尚未确认的共享 API/Schema。依赖接口未确认时，下游不得进入依赖该接口的写入；可先独立做合法只读调查或等待上游确认，不得靠创建新 Agent 绕过。
- 简短任务可直接记录 `no split + factual reason`，不强制画图。不能从依赖图静态无环推定运行时操作一定无冲突，真实现场仍依现有宿主/文件复证。

每个可能并行的 Work Item 在现有《工作流方案》或《实施计划》中记录：`Work Item ID/目标/有效上游/前置依赖/读写集/共享资源/所需宿主能力/允许副作用/验证器/候选结果/根任务汇合时序`。

仅当依赖满足、可隔离写入、目标宿主实际存在原生能力、用户及宿主授权都有效、**有项目事实支持的收益预估**足以抵消额外上下文、协调、冲突与最终整合成本时，选择 `parallel-eligible`；
- 无可信依据不能宣称节省时间，必要时优先 `serial-required`。对于互不写入的独立调查可选 `parallel-analysis-only`；
- 共享配置、lockfile、审批账本、同一站点导航/数据库/端口等无可靠隔离时必须 `serial-required`。无能力/利益不明显时不启动虚构子 Agent 或独立进程。

**并行准入四态与失败出口**：

| Decision Status | 需要的可核实条件 | 允许动作/失败处理 |
|---|---|---|
| `parallel-eligible` | 依赖均满足；真实宿主并行能力、授权、隔离、共享资源约束与收益证据成立 | 可在获授权目标宿主实际派发；真实执行结果另记 |
| `parallel-analysis-only` | 不修改共享/正式文件，只读调查互不干扰且能力/许可允许 | 只并行分析；结果回根任务逐项核验，不推导并行写权 |
| `serial-required` | 同写入面/共享 Schema/lockfile/不确定收益或不具备安全隔离，但原任务串行仍合法 | 保留同一 Work Item DAG，走安全串行，不伪称派发 |
| `blocked` | 关键依赖/公开契约未批准，或权限、危险共享副作用、项目事实不足以支持合法执行 | 停依赖该项的动作并提出补证/授权；**不得把 blocked 解释为可以直接串行执行** |

每项判定记录 `Work Item/决定依据/前置依赖/版本/读写和副作用/消费者/允许或禁止事项/当前真实宿主证据`。当事实实质变化时重新判定，但不以“风险很小”代替宿主真实授权。

---

### 11.2 根任务的唯一责任

**实际比较与复盘**：计划阶段记录是否真正有可比较的串行/并行方案、输入基线、假定收益与额外协调风险；
- 执行阶段分别记录宿主真实 spawn/wait/cancel 事件（无能力则 `unverified`）、可观察执行时间与模型/工具费用（如有）、冲突和返工次数、根任务整合与整体测试结果。
- 若没有可比较样本或成本数据，标注 `not-comparable/unverified`，不能以“并行执行了”证明更快。质量上先确保同一契约与真实消费者回归，再披露效率结论。

- 阶段计划、正式产物的唯一当前版本、确认记录和对外完成结论由根任务负责；子任务只能交付候选文档/补丁/分析及真实局部证据。
- 批次整合前重新读取当前基线、检查候选 diff 对应已批准需求、共享写入冲突、迟到或被取消结果的新鲜度；不能用“已 done”跳过真实对账。
- 按依赖顺序整合后，执行必要集成/回归并在根任务形成唯一可追踪交付。
- 并行/串行质量义务相同；在 Auto 模式下子 Agent 不能直接继承父任务所有操作/批准权限，也不能将产品性建议变成新 Work Item。

---

### 11.3 并行失败与回退

| 事件 | 处理 |
|---|---|
| 宿主未提供原生子 Agent/工具 | 同一 Work Item 计划串行完成，实际并行标 `unverified` |
| 发现共享写入或资源污染 | 停冲突项，改为安全串行或经批准的隔离方式；保护用户 dirty |
| 子任务过时/取消/返回迟到 | 候选隔离，重核需求与源码，不自动合并 |
| Auto 中出现未授权新产品决定 | 受影响链单点暂停请求用户，原有效 Auto 的其他合法分支继续 |
| 整合后的回归失败 | 依实际根因返回相关阶段/批次，旧局部成功不能代替整体成功 |

**资格判定与实际执行记录正交**：`parallel-eligible` 是计划准入判断，`parallel-not-verified` 表示未取得原生派发/等待/取消和对应结果的真实证据；
- 即使资格为 eligible，宿主不可用或未执行时也必须同时记录 `executionEvidence=parallel-not-verified` 并按允许范围串行回退或保持阻断。
- `serial-required` 只说明应串行，若真的完成应有串行执行/整体集成证据；`blocked` 不能因为并行不可用就自动取消上游受保护门禁。
- 不同设备的 parallel 说明文档或 Agent 的文字自报不能代替目标宿主真实结果。
