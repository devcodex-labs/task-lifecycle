# 产物内容与自审契约

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：任意正式文档候选生成/修改/审查/交付、版本确认或外部消费者需要可读产物时。

**唯一主责**：动态 Required/Conditional/Optional、正式 Markdown 文件级自审与内容契约；临时证据分类

**直接消费者**：所有正式 Markdown、阶段/产物消费者、确认记录、公开交付。

**联动 Reference**：`正式专项审查与Finding.md` 管理正式计划/报告，`确认授权与变更.md` 负责审批，`../templates/正式产物最小记录.md`（**从本 Reference 所在目录解析**）仅格式示例。

## 适用时逐项执行

1. 确认产物类型、用户读者、任务目标、当前有效上游、适用专业质量/审批及最终消费者；区分 Required/Conditional/Optional/N/A+reason。原则为**必需内容完整，但版式按任务动态确定**。
2. 正式 Markdown 最低写 Task/Artifact ID、独立版本、事实/批准来源、范围、专业消费者、正文、实际自审方式及问题/修订、未验证/阻断、下一合法动作；不能缺少被触发的独立批准对象或使用契约。
3. 实际编写后对当前**完整正文**做角色/消费者/正反例检查，自主改已授权候选的事实错误并记录 diff 和 whyMissed，再自审到有实质证据支持的收敛或公开阻断；不无限生成报告。
4. 文件内部自审摘要必须指向当前版本，说明谁审（同一AI/真实独立/静态脚本）、覆盖什么、证据上限与未解决项；正式专项审查另有真实被审对象与批准计划，不能用自审代替。
5. 可计算时计算**最终文件字节** SHA（不可计算时按 `确认授权与变更.md`「适用时逐项执行」第 6 条以路径+修改时间+diff 摘要为身份） 只放文件外版本/确认记录，绝不把自身 SHA 写回正文。每次合法修订生成候选新版本并计算差异，不覆盖已签原件。
6. 原始日志、调查草稿、临时脚本、工具输出默认为临时证据，不因改成 Markdown/被报告引用而变正式待批；仅用户或已批准计划明确要求独立正式产物时再生成候选并履行审查/确认。
7. 公开 README/API 只含使用者实用内容，不混入内部审批记录或任务过程；用户能打开/阅读真实候选正文，宿主无文件打开能力则在对话中给可读内容和真实路径，不发明 UI。
8. 字段契约适用时逐实际 fieldPath 查 type/domain、必填/条件、default/absent/null/empty、跨字段约束、成功与错误、安全/兼容/消费者；无字段不杜撰数据库/REST。
9. **ABS-08/AC-107 条件触发的技术选型事实核验**：本批确需新增/升级关键依赖、改框架，或引入重要 SDK/平台 API/宿主能力时，先从当前真实工程记录已用方案、lockfile/已安装版本/运行时版本、真实消费者与必要性，再在已获许可的可用渠道核实**对应实际版本的第一方官方文档、API 用法、支持矩阵及生命周期/副作用**；
   - 对比不引入依赖的已有能力、兼容风险与回退路线。
   - 记录 `选型/真实版本/第一方依据及核验日期/当前安装与实际可调用证据/已有替代/兼容受影响者/决定来源/仍未验证项`。
   - 无合法网络/源码或无法证实官方支持时记 `unverified`，并暂停依赖该断言的写入/交付；不能凭库名、模型知识、Mock 或第三方文章宣称可用。**不是所有任务必联网，也不是允许自行安装或修改用户未批准的技术选型**；不适用记 `N/A+reason`，更优但未批准的方案留在建议区。

## 必须拒绝的反例

- 只核对标题和模板栏目便自评无缺漏；草稿中附“已确认”即当人类已批准；临时30条日志各要求人工批；改动后沿用旧 SHA；公开文档包含内部模型审查日志；同一模型自审称独立专家；凭库名、Mock、旧版博客或未知本机版本批准关键 SDK 选型。



## 完整自审与建议处置（REQ-003/006/007/043）

正式候选提交前，至少进行一次**与生成步骤分离的反向复核**；具备获授权独立 Reviewer 时使用其真实证据，否则由同一 AI 在编写结束后重新读完整候选，明确标注同上下文反向审查。逐一核对：历史版本/失效引用是否残留、适用专业维度是否遗漏、本次改变的全部消费者是否联动、能推翻结论的负例是否成立。记录实际方法、范围、发现、差异和未验证项，不把角色切换或重新算 Hash 当独立审查。

按任务事实扫描正常、异常、边界、状态、并发、隔离、兼容、迁移、性能、安全、集成、反例、误操作及中途变化。每类写适用性、处理/检查/验证责任或具体排除理由；可以在同一简表合并同类义务，不强制为不存在的使用面编造场景。项目确不存在且该项依赖项目时可 `N/A+reason`；项目存在但不可访问或尚未核实应记 `unverified`，说明影响及是否阻断，不能把无证当不适用。

自审同时判断内容是否为实现已批准目标所必需、是否过度设计、是否符合真实使用场景。只有全部适用必需内容及触发条件完整、必要性有依据、反向遗漏已处理、没有未决阻断、状态和证据自洽时才可称候选自审收敛；可选建议无需全部采纳。每个发现记录 ID、原事实/版本、分类、处置/状态及证据：

| 类别 | 合法处置与出口 |
|---|---|
| 已批准范围内、可自主修复的普通工程/事实问题 | 在已有写权内修订未生效候选，记录 diff 并复核；已生效原件另建版本。真正关闭仍消费正式 Finding 和验证门禁 |
| 不影响原目标的可选改善 | 隔离为 `suggested-unapproved/rejected/deferred`，不进入 WI、代码或验收标准，不阻断无关合法工作 |
| 产品/上游冲突、必需证据缺失、重大风险或未授权操作 | 明确受影响门禁与最小待决问题，只暂停依赖部分，交真实用户决定或补证；不能 Auto 代批 |

建议的最低信息为：真实问题与证据、必要性/合理性、必需或可选的判断依据、推荐方案及替代（含保持现状）、各自收益/缺点/风险、时间与引入/维护成本、上下游/消费者影响、不采纳后果和准确待决事项，以及优先级（高/中/低）与理由。
- 报告逐条列出的 Bug/建议另须写明验证状态（E4 实测/E3 静态/未验证，附证据），并至少比较两个可行方案给否决理由；确只有一个合理方案须写明理由。
- 无法观察的成本标 `unknown` 并说明估计依据，不编数字；建议未被合法采纳前不扩大原范围。使用 `../templates/验证与建议隔离最小记录.md` 的建议区；实质变化先按 `确认授权与变更.md` 更新上游。

## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 7.1 产物类别与 Required/Conditional/Optional 分配

| 类型 | Required（最低专业回答） | 条件触发的附加内容 | 不可机械要求 |
|---|---|---|---|
| 任务描述/工作流 | 真实目标、类型/范围、阶段/依赖、适用门禁、合法下一步 | 复杂任务 Work Item/并行依赖 | 固定每个子步骤、全场景无意义章节 |
| 需求/Usage Contract | 对外目标/接口、参数、结果/错误/边界、可验收行为 | API/CLI/UI/文件实际消费面 | 没有 REST 时强行写 REST |
| 完整技术方案 | 对外契约映射、架构、文件/职责、关键实现、异常与验证 | 真实涉及数据库/并发/迁移/安全时相应专题 | 虚构独立 Runtime 或服务 |
| 实施计划/开发记录 | 批次和明确边界、真实 diff、依赖、验证与回退 | 并行隔离、迁移、.http 辅助资产 | 每个函数单独审批 |
| 审查计划/报告 | 对象与版本、角色、动态检查、证据、Finding 与结论 | 专项领域/高风险/实测需求 | 用相同模板固定 100 条测试 |
| 验证/交付报告 | 实际运行/未运行、环境、预期与结果、当前消费者及限制 | Docs 站点/.http/Agent Eval | “执行失败但想象通过” |
| Docs 内容契约/维护文档 | 读者、用途、事实来源、导航/使用任务、维护更新触发 | 已有站点的真实浏览器路径、内部接口消费者 | 纯 README 任务擅自建站 |
| 确认、修订及交接记录 | 版本身份、决策/差异/阻断、可信来源和下一步 | 部分确认、跨会话/旧证据失效 | 通过可编辑记录伪造真人决策 |

每次先判定类型 Required、任务 Conditional 是否命中、Optional 是否有明确价值，再动态组织正文；可把非必需辅助结果并入现有正式文件，但不能合并掉有独立法律/产品作用的使用契约或审查批准职责。

**临时材料与正式产物的分类出口**：原始测试日志、一次性调查草稿、工具输出与暂存分析文件，默认属于可引用的**临时材料或证据**，可以记录真实来源、生成时间/实际版本与引用位置；
- 普通只读报告及其保存也不自动成为正式 Task/计划或独立审批对象；先按路由 §4.3 判定追踪、保存与明确的报告验收要求。必要文件交付失败仍须说明，不用普通/正式分类掩盖缺件。
- 仅因产生了 Markdown、放进 `临时/` 或被正式报告引用，**不自动成为需要单独 AI 正式自审及 Confirm 人工批准/Auto 自动验收的正式产物**。
- 仅在已批准任务计划或真实用户决定要求将其整理为独立正式报告/结论时，才按实际产物类型生成新候选，执行适用自审与审批；原始来源保持可复核，不得通过文件改名、移目录或复制摘要伪称已批准。反例：把 30 个测试日志和临时草稿逐一列为独立待批文件应拒收；但一份已经被识别为正式审查报告的正文仍须履行原有质量和确认门禁。

### 7.2 每份正式过程 Markdown 的自审留痕

自审必须在该文件本身可读，且与当前版本一致。最低应有：自审方式（独立/同一上下文反向检查/脚本/真实工具）、上游有效依据、实际项目事实和未验证范围、适用角色/检查范围、找到问题/修订的差异概要、未解决阻断、待决定的可选建议、是否已收敛/为何未收敛、下一合法动作。逐条完整历史可引用 `审查/`/`修订/`，公开 README/API 文档不应塞入内部自审日志；公开产物由外置过程记录承载其审查证据。

**证据分层**：模型扮演测试者≠真实用户实验；独立 Reviewer 需宿主实际支持且有独立记录；静态编号/矩阵关系对称≠专业语义与真实消费者已核对。每份产物必须允许审查者指出“不适用”与“未验证”不同。
