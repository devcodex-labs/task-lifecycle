# Bugfix流程

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：明确处理当前批准行为违背、已有 Finding 的真实修复或恢复 B01～B10 阶段时。

**唯一主责**：B01～B10 的原问题、故障基线、因果与新回归闭环；Bug A 导致 B 时不能以新任务卸责

**直接消费者**：Bugfix B01～B10、Finding 与回归、实际代码消费者、交付。

**联动 Reference**：`正式专项审查与Finding.md`、`验证与证据分流.md`、`确认授权与变更.md`、`文件目录版本与跨会话恢复.md`。

## 适用时逐项执行

1. B01 确定已批准/真实既有行为与实际差异，不把“客户说 Bug”直接认定根因；B02 在获授权的环境采集复现/未复现、原有正确行为、实际修改面、直接/间接消费者和环境因素。
2. B03 以已证明根因或标记未证假设为基础拟最小修复、适用代码维护质量、回归不变量与安全回退；改变公开契约需真实用户决定，非必要重构仅留建议。
3. B04 写入之前回读当前源码/测试/dirty/许可，限定实际修改；不能为绿灯吞异常、放宽断言、删除既存测试。B05 结合真实 diff/共享消费者/副作用/复杂度/维护性做专项审查并逐 Finding 返修。
4. B06 对原 Bug A、真实发现并证明由此引入的新 Bug B、已有正常行为和共享消费者运行适用回归。若 B 也引入 C，应重评根因/方案而非无限打补丁。
5. 对新异常分类 `introduced-regression/pre-existing-exposed/unrelated-pre-existing/environment-or-test/causality-unverified`；无因果证据不能断言是修复引入。若确认引入 B，则**属于原 Bug A 的修复质量责任**，停交付、关联 Finding、返修并复验 A+B+共享消费者。
6. B07 同步受影响契约/Docs/`.http` 交付；B08 仅独立发布权才能发布；B09 必须有实测和合法用户确认才完成。B10 仅在任何受影响阶段有实质变化时插入。
7. 已记终态后新报告的同版本问题：保留旧终态历史，核实原目标是否未完成/本次引入回归/独立既存 Bug/新 Feature；原责任返修保留关联 reopening；独立 Bug 仅建议另立有权任务，不能静默扩展。
8. 对无法安全重现、涉及真实生产数据/依赖的情况给出准确证据限制和权限需求，不为“必须复现”擅自访问生产。

## 必须拒绝的反例

- 修复原 A 后出现已证引入的 B，仅 A 绿便宣布完成；把 B 新建未授权工单后关闭 A；用 Mock/删测试/宽松断言制造绿灯；因果未知却肯定归因；以 fast 跳过适用共享消费者；未获许可杀旧服务。



## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 5.1 统一阶段协议

每个固定主阶段都必须能回答下面八个问题，具体执行子步骤由项目事实决定：

1. **Enter**：当前任务/上游真实文件身份、确认/授权、现场与前置依赖是否有效？
2. **Role**：主视角、消费者、反向质量视角是什么？分别检查什么？
3. **Plan**：生成该阶段动态子步骤、适用正式产物、验证方式、分解与回退条件。
4. **Generate**：按 Required/Conditional/Optional 生成或更新正式产物；不适用项写理由。
5. **SelfReview**：阅读有效上游和真实项目事实，执行缺漏/反向证据审查；可自主修订至收敛，文件内留下自审摘要。
6. **FormalReviewIfRequired**：专项审查须先有绑定当前对象版本的计划且按模式有效验收，然后按计划执行 Finding 闭环；普通自审不递归新建专项计划。
7. **Approval**：Confirm 逐件真实人工确认；Auto 仅授权内且证据充分的中间产物 `auto-accepted`；报告事实认可不等于对象通过。
8. **Exit/Recovery**：更新阶段证据、合法退出、下一个动作，变更时进入插入式 A10/B10/DOC10；失败时局部阻断和返工，不损害无关工作。

这是 Skill 应引导的**人可读流程协议**，不是系统级无法绕过的事务状态机。退出条件不具备时，宿主可能仍允许用户直接调用工具；插件不可宣称可以全局阻止该行为。

### 5.3 Bugfix B01～B10：阶段输入、产物和关键退出

| 阶段 | 阶段目的与输入 | 必需结果/适用审查 | 退出与返回 |
|---|---|---|---|
| B01 缺陷分析 | 用户现象、当前公开行为与项目事实 | 缺陷诊断方案、环境/受影响消费者及初始假设 | 不把新增功能伪装成缺陷 |
| B02 复现与根因 | 当前源码、日志、环境、已有测试 | 复现证据/不可复现限制、预期与实际差异、根因/未证实假设；直接/间接消费者与既有行为基线 | 无证据不得声称确定根因或假定所有消费者不受影响 |
| B03 修复方案 | 根因与原使用契约 | 最小必要修复、`.http` 条件适用、按实际共享消费者列明行为保持/正反测试、风险与回退 | 公开行为实质变化须人工决定；可选重构不得混入修复范围 |
| B04 执行修复 | 合法方案、旧失败/正常行为与当前 dirty 基线 | 最小必要代码/配置修改、真实 diff/修复记录、原行为保护、必要失败→修复证据 | 发现越界/副作用/不当断言修改先停受影响项 |
| B05 修复代码审查 | 真实 diff、调用入口与行为保持矩阵 | 专项审查计划/报告、共享消费者、项目一致性、最小必要复杂度、可读性/重复逻辑/副作用/可测试性、未批变更过滤 | 必需维护质量和影响面合格，风格建议不无条件阻断 |
| B06 回归验证 | 修后代码与原故障、应保持的合法行为基线 | 原 Bug A、实际存在的新回归 B（如有）和受影响消费者的真实正反/集成验证，适用 HTTP 请求实际结果，区分引入/历史/环境/不明因果 | 必需回归失败或因果未核实时不得假标完成 |
| B07 关联产物与修复交付 | 变更代码/文档/契约影响清单 | 修复报告、公开文档同步、需要时 Docs 站点质量门禁 | 无过期产品文档/验证且交付版本匹配 |
| B08 修复发布（适用时） | 真正发布需求与合法权限 | 发布/回滚证据 | 不擅自 commit/push/deploy |
| B09 任务完成 | 用户原故障目标/当前实际结果 | 原 Bug 与修复引入的回归关闭证据、合法行为保持、维护质量、whyMissed 与交接 | 新回归被另建无授权任务不能据此宣称原任务完成 |
| B10 中途变更（插入式） | 新根因、需求、项目/环境变更 | 更新受影响根因/修复方案/验证/审批 | 按变更后有效状态恢复 |

**诊断来源真实**：测试失败前后样本、日志、数据库/生产数据一律按用户实际授权和可访问性处理；不得因“诊断需要”复制私密数据、运行危险请求或扩大权限。

### 5.3.1 条件性回归影响控制和新 Bug 归属（P0，不新建状态机）

在 B02/B03 从真实项目识别：`changeSurface`（实际修改处）、`directConsumers`（直接调用方）、`indirectConsumers`（经共享 Schema/配置/事件/状态间接受影响的调用方）、`behaviorInvariants`（应保留的正确行为）、`newBehavior`（允许修正的错误行为）和 `validationCases`（适用 D/A/I/H）。这些是**现有修复方案/验证方案中的可读信息维度**，不是必须生成的新 JSON 文件或一次性全仓深读；对无关消费者明确 N/A，有疑问写 `unverified`。

修后发现新异常时，先比对冻结的源码/数据/环境/测试标准，分类为：`introduced-regression` / `pre-existing-exposed` / `unrelated-pre-existing` / `environment-or-test` / `causality-unverified`；若需要改变已批准的**公开契约**则另标 `contract-change` 并触发既有人工产品决定（此为处理路由，不当作由修复引入的 Bug 因果结论）。只有因果证据支持时才将新 Bug B 判为 A 的回归；若引入，关联原 Finding，在原任务中返修，B06 至少复证 A+B+适用消费者；未获批准的独立新任务不能作为 A 完成的替代。B 再引出 C 时必须重新评估根因和策略，避免无界补丁。

**退出条件**：真实执行证据应对应同一代码/测试/消费者版本，并区分 `passed`、`failed`、`unverified`、`N/A+reason`。没有适用环境或重要消费者未验证时按预定质量标准阻断受影响项；`fast` 只压缩不必要文档形式，不能豁免必要的兼容/安全/数据回归。发布/回滚仍须宿主真实授权。

**REV-08 已终结任务的后续问题分流**：若 A/B/DOC09 已记录任务终态，后来收到拒收或同版本新故障，首先回读原有效需求、最终交付指纹、关闭验证及前后消费者/代码证据，判断 `(a)` 原目标未真实满足或原修复导致新的回归、`(b)` 独立已存在且与原修改无因果的 Bug、`(c)` 用户提出新功能/新范围。对 `(a)` 保存原 `terminal/closed` 事实和历史批准，开启具有关联的新返修/必要 `reopen` 记录，受既有授权及受影响复审约束，不抹去原终态；返修必须真实复证原 A、新 B 和共享消费者。对 `(b)` 只登记并建议独立 Bugfix，不擅自开工；对 `(c)` 进入新的产品决定及 A10/B10/DOC10。证据不足标 `causality-unverified` 并先调查，不用创建新任务将原质量责任转移出去。

### 5.5 阶段错误、停止与复原

**已确认变更传播的具体执行协议（R5 受控细化，依据 REQ-008/009/069/073～075）**：出现任务目标、公开契约、技术决策、受影响代码/测试或正式产物的**实质变化**时，受影响操作暂停，创建独立且可读的《变更影响分析.md》（普通未发生实质变化的咨询无需强造），至少记录：真实变更来源及决定、Task/版本/Hash 与适用确认来源、变更前后真实差异、原始 REQ/UC、直接/间接依赖（正式产物→Work Item→源码→真实消费者→测试/Docs/`.http`→交付/发布）、仍有效和需失效的审查/批准/测试、受影响的 A/B/DOC 阶段、允许/禁止操作与恢复条件、应修订文件/版本及独立质量门禁、必要正反回归。对未证实的消费者/传播链标记 `unverified`，不能只凭编号或已存在一份计划声称全链核对。确认记录必须实际绑定本次获批范围，`fast` 可用简洁表格而不省略此有条件必需的变更记录。

**判断和退出**：无真实影响的既有证据可基于明确理由复用；被改变的对象及其关键消费者必须重新核实与按当前合法模式批准。涉及新的产品取舍或公开行为时保留 `suggested-unapproved` 并请真人决定，不把旧 Auto、旧 Hash 或报告事实认可当作新批准。必须确保影响列表反向扫描实际 diff/生成源/打包集合，才能恢复受影响任务链。V1 使用 Markdown 与宿主现有工具，不新增变更传播服务或自动强制拦截。

| 事件 | 应走的技术处置 |
|---|---|
| 重要需求或授权缺失 | 只停止依赖该约束的正式写入/验收，列出需用户决定的精确事项 |
| 当前阶段必需产物未审/未确认 | 退回该产物的有效审查/审批，不绕过门禁 |
| 上游已确认版本实质变化 | 触发 A10/B10/DOC10，评估连带证据失效及可能需要再确认 |
| 外部工具结果未知/写入部分成功 | 先读真实现场、Git dirty、日志，不盲目再次执行 |
| 已存在批准范围内实现错误 | 定位最小修复和回归，不要求重启全部生命周期 |
| “建议更好”但不在已批准范围 | 标为 `suggested-unapproved`，不进入实施任务或测试通过标准 |
| 产品性不可决定 | 给用户理由、优缺点、替代（含保持现状）和精确影响，等待真人决定 |
