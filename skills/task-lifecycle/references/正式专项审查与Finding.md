# 正式专项审查与Finding

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：计划型专业审查、正式被审文件/代码/交付验收、发现 Finding、同根因修订或复审收敛时。

**唯一主责**：专项审查计划先审批、复合子条件证据真实性、Finding 因果与逐项关闭、反无效循环

**直接消费者**：所有正式专项计划/报告、Findings、真实测试、用户批准和有效收敛。

**联动 Reference**：`确认授权与变更.md` 为审批唯一权威，`验证与证据分流.md` 为实际 D/A/I/H 证据标准。

## 适用时逐项执行

1. 先冻结被审当前文件真实版本/外部SHA、准确已批准上游、当前真实消费者与实际项目事实，再制定**版本专属**正式审查计划（检查ID、角色、每条复合子条件、正/反断言、失败判据、D/A/I/H上限、适用性/权限）。计划先自审再按有效模式合法批准；未经批准不冒称正式专项复审。
2. 按批准计划真实回读：来源原文 → 每个适用子条件 → 对应行为与消费者 → 正反检查 → 实际运行/静态证据 → `covered-by-design/partially-covered/needs-evidence/gap/N/A+reason`；`E4` 始终独立，未执行标 unverified。
3. 只知道 ID/章节/标题是 located-only；`covered` 理由若仍写 pending、缺失败出口或未验证消费者，改为部分/待证并记录缺的内容，**不得为了提高计数修改 reason 制造假绿**。
4. 安全地完整收集同轮 Findings 后按真实根因、`defectRootCause`、`controlFailure/whyMissed`、严重性与影响去重；同根可合并最小修复批次，但成员的验证与关闭必须逐 Finding 留证。审查报告事实认可不等于被审对象已批准。
5. 关闭从 open/investigating/repair-planned/repairing 到 verification-pending/re-review-pending 需要真实差异、受影响消费者和适用验证；只有实际核验达到原通过标准、必要复审和合法确认后才能 `closed-verified`。`resolved-in-candidate` 不等于 closed。
6. 发现新 Bug B 若确由 A 修复引入，回到原 Bugfix 任务并复证 A+B+共享消费者；历史独立 Bug、新需求需真实分类/授权。
7. 每轮量化真实新增事实 `newEvidence/newAffectedConditions/newCodeOrContractDiff/newVerifiedClaims/closedWithEvidence`；两轮同方法无实质进展时停止无效循环，分析是否权限、数据、能力、上游产品决定或设计缺口，切合法方法或报告 blocked，不无限制造报告/重问已批计划。
8. 报告准确 E1/E2/E3、E4/独立 Reviewer 状态；同一模型不同角色不是独立人。只有按冻结适用条件全面满足才建议对象质量通过，真正完整批准仍由当前有效权限负责。
9. **同一计划的一轮连续审查**：计划/范围/版本与有效授权未失效时，可分技术批次持续收集全部适用证据、按根因合并 Finding，修订已获写权的未生效候选、回读差异和逐 Finding 自审/复审，最终**集中**列出可证结论、未验证项和真正待人决定的独立对象。
   - 中途新报告、新 Finding、子批次和重跑非破坏性自审不自动触发人批，也不需每一轮虚造新正式报告。
   - 若出现新产品选择、已批准原件变更、计划实质失效、高风险宿主操作或最终人工验收，仅暂停所依赖的部分并按 `确认授权与变更.md` 精确申请；不得以连续工作为由把未经许可的代码写入、E4 或批准生效自动执行。

## 必须拒绝的反例

- 自动章节匹配就签566项 E3；理由明写仍待审但状态 covered；两个 Finding 同根只验证其一便全部 closed；把模型自审三轮写成三位独立 Reviewer；同计划每批都需重复批准；CI/flaky 未测完成仍通过。
- 同一个有效审查计划拆三批就三次索取“确认继续”，或因发现五个 Finding 产生五个无独立生效义务的审批报告：拒收；但两份确需人工生效的不同正文即使集中展示，也不可用一次含糊“好的”替代逐件确认。



## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 7.4 动态审查计划协议

正式专项审查计划包含：`Plan ID`、当前对象/版本/Hash（若可计算）、有效上游及项目事实快照、审查目标和排除项、按角色的检查 ID/理由/证据方法/正反例/通过与失败条件、环境与成本/授权、Finding 分级和修订重审规则、需要人工决定的未决事项。

计划生成后先自身自审，再在当前模式下有效验收；未经合法计划确认不得开始**正式专项审查**。计划批准后被审文件、上游、实际消费者或关键项目事实发生实质变化时，先分析原计划是否失效；失效则重做受影响项并重新确认，不能沿旧报告放行。

**普通文件 AI 自审与正式审查严格分离**：普通自审不递归生成新专项计划，否则导致无限生成；正式审查失败生成 Finding、修订并复测，仍需向用户呈现报告事实与对象质量两种不同结论。

**事前冻结的子条件判据**：正式计划至少在适用时列出 `Source ID/完整获批准义务 → 子条件及触发前提 → 真实读者/实现消费者 → 对应技术行为/失败与恢复 → 可否共享验证 → 预期正/反断言 → D/A/I/H及证据上限 → 非适用理由/阻断`。
- 为同一条复合要求的多个义务分别说明签署依据；已经有完整单一段落能够支撑全部条件时，一个锚点足够，不为了凑数强制多锚点。
- 计划批准前冻结已知质量判据，计划批准后实际新增风险/事实漂移时先判断是否需要受控修订计划及原模式有效确认；不回溯声称旧版已检查新风险。
- `inventory/章节链接/自动拆句` 只可生成检查候选，不可批量自动写 `covered-by-design`。

### 7.5 Finding 生命周期与根因区分

**分类与集中处理协议**：正式审查在安全且无破坏性副作用条件下先收集同轮全部可核实 Finding，冻结含 `Finding ID / 审查对象版本 / 真实证据` 的快照；
- 再进行分类（实现缺陷、已批准上游或方案缺陷、测试设计、交付、独立历史 Bug、新产品需求、重复、误报）与因果核查。
- 仅在有共享根因、来源与实际依赖证据时将多个 Finding 组成共同**修复批次**，记录 `parent/groupId → 原 Finding IDs → 根因/依赖 → 改动版本 → 各项验证/复审结果`；
- **修复可合并，验收必须逐 Finding 独立完成**，未得出结果的成员保持开放。
- 重复/误报只能用原样证据注明 `duplicate-of / rejected-with-evidence`，不得假称已修复。
- 发现危险命令、证据污染或互相矛盾的审查意见时停止相关步骤，以原始事实、真实消费者和冻结标准裁决；无法解决则记录冲突及补证条件，**不能按 AI 角色投票多数决定**。
- 超出原批准范围的独立 Bug 须另经用户授权，修复引入的回归不得移出当前原任务质量闭环。修复批次并行仍须执行 `任务拆分并行与整合.md` §11 的单写者/依赖/隔离判断。

每项 Finding 至少记录：`Finding ID`、发现的要求与检查 ID、当前对象/版本、事实与实际证据、严重度（P0/P1/P2）、缺陷根因 `defectRootCause`、原审查未发现的原因 `controlFailure/whyMissed`、影响与建议、必要人工产品决定、修订 diff、受影响上游、重新验证结果、关闭状态。

- P0/P1 的必要质量风险未解决，不得放行被审对象；发现的 P2 按已有通过条件和实际风险判断，不为了清零制造重复无价值的修订轮次。对于修复 A 引入 B 的因果证据，B 必须关联原任务/修复版本并保留所需复证，不允许通过分拆工单或仅调整测试期待绕过质量归属。
- `resolved-in-candidate` 是**候选文档已修改的事实**，不是 `closed`；关闭需要对应复审及实际证据等级，再按合法模式确认报告的准确性。
- 实现偏离/已批准契约变化/环境变化/无来源代码修改/建议误实施分别按既有 REQ-065～077 路由；有必要时回到上游 A/B/DOC 阶段，而不是只改自审文字让代码与合同自洽。
- whyMissed 经泛化资格核实，可以提出改进已有 Reference 或通用规范候选；没有通用证据不得自动上升为长期规则。

**逐 Finding 可判定关闭合同**：每条从 `open/investigating` 至候选修订后，逐一保存 `原始缺陷与约束版本 → 修订 diff/真实修改对象 → 应保持的消费者/条件 → 验证器及其版本/真实结果 → 必需正式复审计划与复审报告 → 可信报告事实/对象确认状态 → remainingRisk`。
- `verification-pending` 在适用验证实际未结束/失败/未授权时保持开放；
- 验证满足已冻结标准后进入 `re-review-pending`，由适用专业审查核对范围、根因/whyMissed/新回归；
- 审查完整且本任务合法门禁都满足时方可建议或登记 `closed-verified`。
- 同根因修订可以统一一批，但独立子 Finding 不能复制父 Finding 的关闭结果。
- `rejected-with-evidence`、`deferred-approved` 是与已修复关闭不同的合法出口；历史 `closed` 无相应证据不得补签。
- **阶段性用户认可审查报告事实并不证明设计对象质量通过**，不得触发 Finding 的无条件关闭。

### 7.6 自审循环停止条件

发现可自主处理的、在已批准范围内的事实错误时记录 diff 后重审；重复轮次应检查新证据/根因是否推动质量改善。没有新增信息仍然不收敛时停止无效重复，写 `blocked` 与所需精确补证/产品取舍，不降低标准。可选的改善建议不影响原产品目标完成时可作为 `suggested-unapproved` 留存，不因此让合法产物无限等待。

**实质进展与无效循环判定**：在既有审查/修订记录中记录每次复审真正增加的 `newEvidence/newAffectedConditions/newCodeOrContractDiff/newVerifiedClaims/closedWithEvidence`，以及仍开放的条件和 `controlFailure/whyMissed`。
- 仅重复原问题、改变报告名/版本、把 `needs-evidence` 改成 `covered`、把 38 个受影响 ID 误当 38 个新功能，不构成进展。
- 连续使用相同方法而无法带来可复核的新证据时立即停同法重试：先按根因判断是缺数据、技术缺口、用户决策、宿主能力/权限，合法切换核验方法、集中一个最小修订批次，或公开阻断与所需补证；
- **重试上限**：同一失败经两轮不同方法的修复/核验仍未通过（含 A06/B06 反复失败），即公开阻断，请用户在缩小范围、退回 A03/B03 设计阶段或终止任务之间决定，不创另一个“无限重审”循环。工作底稿不为进度统计而升级为必须批准的新正式报告。

### 7.7 条件性字段级契约审查协议（已采纳质量细化）

**触发**：真实被审对象存在 API/SDK/CLI 输入输出、配置、事件、内部接口、持久记录/任务 Markdown 状态字段，或本次变更涉及字段语义。没有这些字段时明确 `N/A + reason`，不为了审查虚构 REST/数据库/JSON 接口。

每个适用的真实字段路径（包括嵌套项）至少应被以下可核验语义覆盖：`fieldPath / direction(input|output|record) / consumer / requirementSource / usageScenario / typeAndDomain / requiredConditionalOptional /
defaultAbsentNullEmpty / crossFieldConstraints / successResult / errorResult / securityAndPrivacy / compatibility / evidenceOrUnverified / reviewDecision`。
- 可按类型相同、约束完全一致的字段组共享审查方法，但仍须逐路径标识覆盖；
- 高风险/公开兼容/鉴权字段不能只用 Schema 类型对照代替必要性及语义判断。

执行顺序为：已确认源需求与实际消费者 → 实际字段 inventory（源代码/契约可访问时） → 每字段来源、必要性、合法值、默认/缺省/null/0/false 区别 → 多字段互斥/依赖/组合 → 成功/错误/敏感输出 → 版本迁移与消费者 → 正反验证/实际证据 → Finding 处置。**一个字段是否合理的结论必须能回指获准需求或者必要工程理由；额外产品字段只能提案不得擅自增加。**

对没有可访问真实项目的当前技术方案审查，只能证明本协议的设计完整和待验证例，不能宣称已经实际验证了用户项目的每个字段。`static-schema-passed` 不能冒充 `scenario-semantics-verified`。

### 7.8 审查覆盖与证据强度声明

每份审查结果必须区别 `inventory`（只知道对象集合）、`search`（关键词/符号索引命中）、`sampling`（可重复样本）、`file-deep-read`（实际完整深读）和 `runtime-consumer`（实际消费者/运行证据）。
- 记录对象全集、实际读到的文件或条款、排除项、版本、失败/未验证项，不能因 Hash/标题/统计行号存在而宣称语义逐项通过；角色视角名录不替代真实证据。

**E3 设计结论与 E4 运行状态分离**：对每个现行源 ID 保持至少以下人可读判断：`located-only`（只找到源/章节）、`partially-covered`（某些子条件设计存在）、`covered-by-design`（全部适用子条件的 E1/E3 设计依据、消费者和正反断言完整）、`gap`、`needs-evidence`、`N/A+reason`；
- `E4` 独立列为 `unverified/failed/passed/N/A+reason` 并附实际授权及执行证据。
- E3 `covered-by-design` 与 E4 `unverified` 可同时成立，**但不能据此声称实现已通过、目标宿主可用或端到端验收成功**。
- 如相应设计子条件、消费者、失败出口或独立条件签署仍 `pending`，禁止同时标 `covered-by-design`；
- 应保留 `partially-covered/needs-evidence` 并指出缺哪一项。
- 提交统计/审查报告前做双向一致性检查：`有效源/版本/Hash ↔ 适用条件 ↔ 实际技术段落 ↔ 证据等级/执行者 ↔ 正反判据 ↔ 当前状态/reason ↔ Finding/权限`。报告只使用校验无矛盾的逐项结论计数；
- 历史 `covered+pending` 必须保留原记录并另做纠偏，不能直接修改 reason 来制造通过。

### 7.9 固定版本集中发现与成批修复

本节细化§7.5～7.6的执行顺序，适用于Feature、Bugfix和Docs中的审查/返修；不新增主流程、审批对象、强制文件数量或运行时机制。

1. **冻结一轮发现范围**：记录当前对象版本/Hash、有效上游、有限检查清单及每项预期/失败条件。优先复用同版本已有有效结果；对安全且可独立执行的剩余检查连续发现、保留原始失败，发现首个问题后不立即改被审对象，使后续结果混入新版本。发现阶段以清单各项已有可核实结果或明确未执行/阻断及影响为出口，不承诺发现全部潜在Bug，不为清零无限扩展范围。
2. **前置阻断例外**：启动/环境等故障使后续检查无法执行，或存在危险副作用、证据污染时，只暂停相关路径；按现有权限进行必要最小处置，记原失败、处置diff和新版本，再继续剩余发现并复核确受影响项。不得以“先收集全部”为由卡死，也不得未经影响分析重启整个任务。
3. **冻结问题快照并归因**：按§7.5分类、核对原批准范围及`defectRootCause/controlFailure`，分别识别产品缺陷、测试/环境/证据交付问题、重复/误报和可选改进。仅因同时失败、措辞相近或共享报告不能合为同根；只有真实根因/依赖证据充分时才归共同批次，保存原Finding ID与失败样例。
4. **成批修复并逐项验收**：根据根因、共享消费者和实际依赖安排最小批次；无证据关联的问题分批，有依赖先后处理。批次内可进行每项必要最小验证，但不每改一个问题就重复整套工作流。批次和最终验证执行`验证与证据分流.md` §10.7；共享修复不能复制成员关闭结果，每项未达条件仍开放。
5. **收敛与变更**：修复引入的新回归留在原任务，重新核对根因与影响；新事实使冻结清单实质失效时，只修订受影响范围并按现有合法模式处理。无新事实的同法循环按§7.6停止；普通P2/可选建议按既有质量门禁决定，不为无限追求零缺陷拖延合格交付。新产品决定、独立Bug越界、最终真人验收和外部操作仍按原授权处理。

上述版本、检查快照、批次依据和退出事实可写入已有计划/Finding底稿；不要求每轮新建正式报告或重复人批。必须拒收：边发现边修改却把混版结果当同轮完成、把工具/包装错误计为产品回归并全流程重跑、没有因果依据地合并关闭，或为少跑测试省略真实受影响消费者。

### 7.10 接力审查（多审查会话，串行）

**触发**：正式专项审查计划使用两个及以上审查会话（外部审查 CLI 或宿主独立会话），或计划要求独立审查方。计划（§7.4）须写明审查方池、席位与棒次顺序、各棒侧重点和独立程度，并满足第 8 条的第一轮全量计划要求。
本节细化§7.9，不改§7.4～7.6的计划、关闭与停止条件，收敛按第 7 条风险分级判定。

0. **责任与授权边界**：审查会话只产出“审查意见”，是待核实的输入；正式审查结论、Finding 定性与关闭、E1～E4 判定和批准仍由当前宿主的协调方负责，
   协调方对每条意见回读原文逐条核实后才采纳（同§7.5，误报写 `rejected-with-evidence`）。
   - **与外部编码执行器委派的边界**：外部 CLI 用作审查会话时，只做只读的意见收集，不承担 FormalReview 的任何结论、签署或关闭；
     `任务拆分并行与整合.md` “外部编码执行器委派”节的默认关闭、类别配置和“永不委派”清单不因本节放宽，该节的委派约定也不能启用审查会话。
   - **准入**：仅当真实用户本次明确指令点名该 CLI 用于本次审查（用户决定，不是委派约定），或今后经用户确认生效、专门列出审查方池的约定时才调用；
     否则按第 6 条按零家处理。调用仍遵守该节第 3 条能力探测、第 4 条中除写入许可外的调用约束（无界面、断网、禁免确认、禁写）和第 6 条留痕；
     读取范围仍按该节第 4 条须限制读取；只限写不限读的档（如只读档）仅在真实用户本次指令明确点名该档时使用，并记录该读取范围为残余风险。
   - 说明（不改本条含义）：放权类配置的 `review` 节是上句「已生效约定」的一种形式，按 `任务拆分并行与整合.md`「放权类配置」消费协议第 9、10 条读取；
     委派节配置仍不能启用审查会话。
     各棒之间的信息边界另按本节第 1 条执行。外部 CLI 之间或同一模型多会话的互审标为非独立 Reviewer（同该节第 5 条）。
   - 协调方是正在修订的主会话，可以核实和裁决意见，但不能充当任何一棒的审查方或终核方。
1. **轮、棒与串行顺序**：一“轮”绑定一个冻结版本（记 sha），本轮内被审对象不改；同一冻结版本可连续审多轮（如只修送审材料后重审），每轮仍有独立轮次编号。
   每轮按下列顺序一棒接一棒进行；
   前一步交卷、协调方保存并当场记 sha（之后不可改）、完成该步要求的核实后，才启动下一步。每次调用都新建会话。
   - **首棒（席位 A，默认侧重“能否照着执行”）盲审**：给冻结版本、范围、侧重点、已批准审查计划（检查 ID、正反判据）和必要来源清单；
     不给任何其他审查会话的发现、核验或总体结论（本轮和以往轮次都不给）。
   - **协调方核实首棒**：对每条回读原文，标采纳 / 驳回（附原文证据）/ OPEN（依据不足，写明缺什么），形成“首棒已核实清单”：
     每条只含 ID、位置、问题、证据和协调方裁决，删去“已收敛”“其余无问题”等总体结论以及 whyMissed 和建议。
   - **次棒（席位 B，默认侧重“漏洞与冲突”）**：审同一冻结版本，提示词内联首棒已核实清单（只按上述格式）。
     仍须对给定范围独立做全量覆盖并输出自己的覆盖清单；不得只审首棒条目，也不得把该清单当作范围；
     对首棒条目可标同意 / 异议（附原文证据）/ 补充；自己的新问题单列，单独计数。
   - **终核**：另开席位 A 的新会话，给次棒的新问题以及对首棒条目的异议、补充（只含 ID、位置、问题、证据，删去总体结论），
     并给同一份已批准计划与必要来源；逐条标采纳 / 驳回（附证据）/ 补充，依据不足标 OPEN，不凭清单摘引裁决；清单外的新问题标“核验中新增”并计数。
   - **裁决与下一轮**：协调方对本轮全部条目逐条裁决（同§7.5）后，才修订并冻结下一版；下一轮的任何一棒都不得提前启动。
     不用未绑定本版的旧清单。中间轮的范围变量只写章节/行号范围、检查 ID、指纹和依赖，不写任何 Finding 的问题描述、证据、关闭依据或核验结论；
     例外只有两项，且须按本条规定的字段：次棒内联的本轮首棒已核实清单；终核内联的本轮次棒新问题及对首棒条目的异议、补充。
   - **同类扫描**（修订前）：某条已采纳 Finding 属于一类问题（如错误引用、同一改动面漏列、被沿用的旧句）时，先用脚本或检索扫出全部同类实例，一次批量修正，
     并在记录里写明扫描命令和命中清单。命中项逐项分类：只修订已获授权的当前消费者；历史版本、已签原件、备份、失败证据等历史实例保留不改，
     并记录排除依据（与 `candidates/archived/CAND-20261024-010-修改后联动残留与缺席检查.md` 一致）。
   - **信息边界证据**：首棒不得读到任何其他审查会话的输出（本轮或以往的报告、核验、任务记录）；次棒除内联清单外、终核除内联条目外，同样不读其他审查输出文件，
     以免读到未核实原文、whyMissed 或总体结论。每次调用不恢复、不继承含其他报告的历史或摘要；记录会话 ID、实际输入清单和读取边界。
     审查方沙箱能限制读取时，其他审查输出不放在可读范围；不能限制读取时（如只限写的只读档），不提供这些路径，
     并在会话日志可完整记录读取动作时，事后核查确无这些路径的读取，记“读取未隔离、日志核查”，可计入本节；日志不完整或核查发现读取过，该棒不计入。
     送审的被审材料（含候选版本记录与自审）与登记行同样不得载入本被审对象以往各轮的审查意见（Finding 的 ID、问题、证据、whyMissed、裁决或修复摘要），
     改引外置裁决或快照的文件名＋完整 sha256；上一版到本版的 diff 只含被审文本改动，不附 Finding 映射。
     正式原件按 SKILL.md 与候选模板保留文件内自审摘要（自审方式、适用检查、当前版本、修订依据、未验证与待确认范围；差异概要按 `产物内容与自审契约.md` §7.2 写到改动面一级），
     不写逐项修复叙述，逐版改动说明放外置记录；
     送审副本中，被审对象当前副本、全部基线副本（上一版及任何历史版本）与全部 diff 的自审与版本记录一律替换为占位（外置文件名＋完整 sha256），冻结原件不改；
     本轮冻结记录同时写原件与送审副本的 sha256 及占位映射（副本位置→原文位置），审查方核对副本 sha，协调方核对原件 sha。
     送审的全部基线副本与 diff 按同一要求脱敏（以占位行注明外置文件名＋完整 sha256，冻结原件不改），送审前检索复扫并记录命令与命中。
     例外（可送审的来源事实）：候选模板 `Actual Finding IDs / Source Evidence` 与 `defectRootCause / whyMissed / controlFailure` 字段所引的
     其他任务或审查的原始缺陷事实，须在送审前冻结，只写事实、任务/审查 ID、版本与 sha，不写对本被审对象的评价或裁决；超出这两字段的不属例外。
2. **固定模板**：首棒用 `templates/接力审查首棒提示词.md`，次棒用 `templates/接力审查次棒提示词.md`，终核用 `templates/接力审查核验提示词.md`；
   冻结后不随轮次改，每轮只换模板中的变量；不得随轮次临时改写模板正文、审查范围或提示口径。
   经轮次裁决确需修订模板时，作为受控修订：记新模板版本、裁决依据（文件名＋sha256）与起用轮次，旧版原字节留存，自下一轮起使用。
   审查会话只在回复中返回结果，由协调方保存并计算 sha。
3. **覆盖清单与 whyMissed**：首棒和次棒都必须输出逐段覆盖清单；每条问题带 whyMissed 及证据，证据不足时写“待核验”及缺什么，不得虚构。
   “待核验”只是审查方的临时标记，不算已写 whyMissed：协调方须补成漏因类别加证据（漏因类别见第 9 条「术语」），补不出证据按未写处理。
4. **判新、收敛与带偏监测**：各棒报原始问题；协调方在各棒结果冻结后对照本轮开始前全部有效的 Finding 快照（含同一冻结版本此前各轮；次棒另对照首棒已核实清单）去重，
   分别记首棒、次棒的原始数、去重关系和实际新增数，以及终核中新增数。
   - 收敛按第 7 条风险分级判定，复审范围按第 5 条。
   - 带偏监测：每轮记录首棒新增数、次棒新增数、终核中新增数。次棒持续只复述首棒（新增为 0）而终核或下一轮首棒出现新增时，
     轮换席位侧重点或缩小中间轮范围。
   - **逐轮数据记录**：每轮按棒记录耗时、成本（可得时）、新问题数及其落点（改动段 / 未改段），用于下次判断。
     某席位已连续多轮为 0 时，仍照常跑各轮，不减少席位或棒次。
5. **复审范围**：第 2 轮起只审改动条款及其直接消费者，高风险档并全量回归全部冻结用例；每轮照常提供完整来源清单，审查方可随时回读。
   “审查方席位”是跨轮稳定的身份（如“codex 席位 A”，绑定 CLI/模型与侧重点），每次调用仍新建会话；新加入或更换 CLI/模型的席位不继承其他席位的覆盖。
6. **审查方家数降级**（如实标注独立程度，不减少检查）：审查方池按第 0 条从用户指令或已生效约定读取。
   - 说明（不改本条含义）：`review.fallback` 三个固定值逐字对应下列三档；候选池＝用户本次点名的 CLI ∪ 有效 `review.hosts`（`review` 省略或 `enabled:false` 不否定本次点名）；
     对候选逐一做第 0 条准入与能力检查后，按**实际可用家数**落入下列各档（实际可用为 0 即零家，含点名 CLI 失效或中途不可用）。
   - 一家外部：次棒由当前宿主新开独立干净会话。宿主开不了独立会话时，用该外部审查方的隔离会话分任首棒、次棒和终核，侧重点不同，
     标“同一模型（X）两个独立会话，无跨模型互补”。
   - 零家：当前宿主互不相通的干净会话分任各棒，标“同一模型两个独立会话”。
   - 标注释义（协调方解释，Rocky 可推翻）：上两档标注沿用 Rocky t323u 原文不改；其中“两个独立会话”指两个审查席位（A、B），
     首棒、次棒、终核每次调用仍各为新会话，会话 ID 逐棒记录。
   - 一个独立会话都开不了：没有合法的审查方，独立审查条件记 `blocked/needs-evidence`，不得由主修订会话轮换侧重点冒充；
     协调方仍须完成自审（§7.4 普通自审），在最终报告残余风险写明“无独立审查方”，并请用户决定补配审查方或接受该风险。
   - 中途不可用：按上述降级，记录自哪一轮起及原因；不沿用此前两家结论；同一模型不得称跨模型审查。
   - 三家及以上外部：不另设规则、不增加棒次，按第 0 条准入与本条同一规则安排：每轮从池中选两家分任席位 A、B，其余记“未选用/替补”，
     计划写明每家本轮的安排（担任的席位或未选用/替补）。
7. **按风险分级收敛**：
   - **分档**：低风险＝内部流程规则、模板、说明文字等可回退改动；高风险＝改公开行为或契约、发布、权限或授权、删除。
     协调方提出分档并写理由，Rocky 确认一次；拿不准按高风险。Rocky 对某次审查的具体指令（如指定轮数）优先于本条默认。
   - **低风险**：只跑一轮（席位 A 首棒→核实→席位 B 次棒→终核，串行不变）；零核实成立的 P0/P1 即可交 Rocky 晋级；
     有核实成立的 P0/P1 时不生效，修订后复审，复审按第 5 条范围，连首轮合计最多 3 轮，到顶交 Rocky 决定；复审后零核实成立的 P0/P1 即可交晋级；
     P2/P3 记为已知缺口（核实成立的 P2 须先按第 3 条写好 whyMissed 再交晋级），晋级提交中逐条登记到 `docs/已知缺口.md`（编号、级别、来源候选/提交、问题、whyMissed 链接、状态），INDEX 行与 CHANGELOG 只写条数并指向该台账；
     真实使用后在修订提交中修，同一提交把对应行改为 closed 并写关闭提交。本条也适用于高风险档到顶后 Rocky 决定接受的缺口。
      交晋级前全部 OPEN 须先裁决；可能为 P0/P1 的 OPEN 未裁决时不得交晋级，仅“零核实成立的 P0/P1”不足。
   - **高风险（用例驱动）**：审前协调方拟 8～15 个具体用例（输入＋期望结果），Rocky 确认后冻结；审查员拿规则逐用例跑；
     Finding 须写明失败用例 ID 和失败步骤（或违反的不变量 ID 加用例步骤或条款行号，见下文不变量项），否则记为“新用例提议”交 Rocky 决定，不阻断收敛；第 2 轮起按第 5 条复审并全量回归；
     全部用例通过且零 OPEN 即收敛；中间轮最多 3 轮，到顶即停，把剩余问题交 Rocky 按已知缺口决定（P0/P1 须 Rocky 明确决定，不得默认接受）。
     Rocky 中途收下的新用例提议加入用例集，自下一轮起一起回归；轮次不清零，封顶仍为 3 轮；第 3 轮中收下、尚未回归的用例记“未验证”，随剩余问题交 Rocky，不开第 4 轮。
      **Case-Driven Convergence（用例驱动收敛）V2**：本高风险档定名于此，以 Rocky 8 条原则为框架（验收基线先于审查确定；用例＋不变量；发现须有证据；
      最小变更、禁无授权治理扩张；增量复审＋全量用例回归；风险审查有明确边界；自动修复最多三轮、失败升级、不自动通过；非阻断改进另立候选）；本条「分档」是入口。
      - **不变量**：协调方拟用例时同时拟 4～8 条不变量（每条：ID、必守条件、判定方式），与用例一起交 Rocky 确认后同时冻结；
        每轮各棒逐条检查全部不变量，在覆盖清单中逐条记“守住 / 违反（附用例 ID 与步骤或条款行号）”；违反任一已冻结不变量即为有效 Finding，与用例失败同等处理；
        收敛须全部用例通过、全部不变量守住且零 OPEN。新增或修改不变量只能由 Rocky 收下，按上句“收下新用例”同一规则计轮。
      - **探索边界**：审查范围＝冻结的用例＋不变量＋（第 2 轮起）改动条款及直接消费者；用例与不变量之外的意见只能作“新用例/不变量提议”，
        每棒最多 3 条，须写明拟用的输入与期望结果，不计 Finding、不阻断收敛、不进入当轮修复；超出条数的由协调方记录条数但不转交；
        第 1 轮之后不得新增审查维度或检查项（Rocky 按上述规则收下的不变量与用例除外）。
   - **中途升档**：审查中发现低风险改动实际触及高风险范围（如授权条件）时，暂停审查，改按高风险，先补用例交 Rocky 确认后再继续；升档前已跑的轮次计入 3 轮封顶。
   - **修复不加新机制**：本版修复只能删改或做最小改动；需要新机制（新脚本、新送审材料类型、新命名或比对规则等）的，另立候选；
