# 角色与专业审查

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：产物有专业完整性/实施质量风险，必须制定动态审查检查项或发现专门 Skill 候选时。

**唯一主责**：按实际任务和材料动态选择阶段、产物与正式审查三级角色视角和证据，而不制造独立 Agent 人数

**直接消费者**：所有阶段/正式产物/动态正式审查计划，适用 Skill 主辅选型。

**联动 Reference**：`正式专项审查与Finding.md` 为审查覆盖签署权威；`Skill发现匹配与能力降级.md` 决定可用能力。

## 适用时逐项执行

1. 对当前阶段明确实际主责视角与逆向风险视角；产物层另明确最终真实读者/实现/维护消费者；正式专项审查层按冻结任务事实选择专家检查内容及证据。
2. 输出 `role/viewpoint → source clause → check question → expected positive and negative → method/evidence → actual observed status`，角色名称本身不是检查结果。
3. 一位模型可以采用多种视角做**同一上下文反向审查**，必须诚实标注非真实独立 Reviewer；真实独立 Agent 仅宿主支持且获授权，有可回读独立记录时才写独立。
4. 同类型任务合并冗余视角可以，但不可因精简省略权限、测试、兼容、API字段、使用者验收等已触发检查。
5. 需要专业 Skill 时优先核查当前可用与可信性，再按 `Skill发现匹配与能力降级` 选择/降级，不为一个角色名称强制安装额外 Skill。
6. 核实结论可复核版本、真实消费者、负例及未证范围；审查意见冲突用事实与冻结标准判断，不能用多角色模拟投票确定公开产品决策。

## 必须拒绝的反例

- 生成“资深测试员/安全专家”姓名列表就判专业审查已完成；同一模型反向检查伪称三个独立评委；把官方市场第三方条目当官方认证；用户尚未批准公开行为修改却用架构师视角代批。

### 7.3 三级角色质量契约：阶段、产物、专项审查

| 层级 | 谁选择 | 产出与最低可核验内容 |
|---|---|---|
| 阶段角色 | 主任务在 00 和每个阶段入场时，按当前目标/风险动态选择 | 主要负责视角、必要反向视角，各自的检查责任、失败条件、退出证据 |
| 产物消费者 | 编写者依据有效需求与真实用途选择 | 主要读者、实现者/维护者、用户最终任务，Required/Conditional 与遗漏风险 |
| 专项审查角色 | 经合法批准的审查计划动态确定 | `角色 → 检查项 → 实际依据 → 方法 → 已执行/未执行 → 发现/结论`，每项可追踪 |

例如技术设计一般需要架构师视角核查设计选择、实际实现者核查可实施性、测试者核查验收/反例；Docs 站点还可能需要首次使用者、现有 API 使用者及维护者视角。角色视角只是专业问题集，**不是现实员工编制、不是单独 Agent 证据，也不增加产品决策权**。小任务角色相近可合并，但要覆盖核心问题；无关角色按 `N/A + reason`。

### 8.1 角色、Skill 与执行者是三种不同概念

- **角色**：描述从哪一类消费者或专业责任视角提出检查问题。
- **Skill**：提供可能的专业规则/工具使用方法，只有确实可读取、可使用时才是可用能力。
- **执行者**：当前模型、真实受授权子 Agent/Reviewer、实际工具或真人；模拟角色不等于真实独立执行或专业资质。

不能因为提出了“架构师/安全工程师”角色就自动安装或创建同名 Skill，也不能因为发现 Skill 便跳过本插件的审批、证据与工具权限。
