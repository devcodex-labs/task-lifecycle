# 验证与证据分流

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：任何需要声称代码/任务/文档/规则已验证，或选择安全测试器、运行CI/HTTP/Agent Eval，或准备真实提交、打包、分发/发布候选时。

**唯一主责**：D/A/I/H质量声明与真实测试、CI/flaky、Agent Eval污染隔离、历史失败与实现反向符合性、交付集合与真实消费者反向核验

**直接消费者**：A06/B06/DOC07、Finding关闭、PoC、项目验收与交付。

**联动 Reference**：`HTTP辅助验证.md` 给.http四态；`Docs受众与站点质量.md` 给读者任务；`正式专项审查与Finding.md` 决定闭环门禁。

## 适用时逐项执行

1. 针对当前受批准需求的每个**适用质量声明**明确正确性 oracle、正常/反例、目标源码/消费者版本、D（确定性）/A（Agent行为）/I（集成）/H（真实用户决定）检查责任及实际授权；工具可用不等于应运行。
2. 项目事实优先：只读核实真实现有测试脚本、语言、CI配置和 Git dirty；先复用项目已有可安全执行的路径。未看到源码时不得编造 `npm test`、浏览器或完整兼容通过。
3. `D/A/I/H` 各自记录 `expected / actual / environment / version / commandOrAction / time / evidence / permission / status`。没有实际执行时 `unverified`；真正不适用需 N/A+reason；blocked/failed/unknown 与 passed 不混。
4. `CI queued/running/cancelled/unknown` 不等于 passed；flaky 调查保留失败历史与运行参数、重跑范围和稳定性结论，不因最后一次 green 擦去之前真实失败。
5. Agent Eval 需要冻结 rubric、正/反样例、真实支持的 CLI/模型权限、隔离工作区/dirty快照、资源范围与退出/清理方案；同一AI自评不能当独立 Agent Eval。无权限/工具/隔离时不运行、明确 E4 未验证。
6. Bugfix 真实回归包括原 Bug A、已证本次引入 B、共享消费者/行为不变量和受影响代码版本，不能只测一个局部函数。Docs 需实际读者导航/使用任务与真实页面/接口，build仅D证据。
7. HTTP `.http` 生成、静态解析、实际请求、请求断言 passed 为四级分别记录；实际请求须在当前任务及宿主允许的准确环境/数据范围内。发布、下载依赖、启动服务等同样核对真实副作用和现有范围，不因本规则另加逐次操作批准，不覆盖宿主拒绝。
8. 最终以根任务整合后的同一实际代码/产物/环境版本校验，并区分设计E3、真实E4、CI原始状态、人工批准事实。
9. **ABS-07/AC-106**：只在真实提交、打包或发布候选需要形成交付集合时，先只读核实工作区与获准交付范围，列出 `working / staged / untracked / generated / ignored` 的源文件、被正式产物引用的文件和实际包/提交目标；
   - 以批准来源与真实消费者反向逐文件检查 `includedInDeliverable`。
   - 漏了必需生成物、未追踪文件、被忽略却需交付的资源、可执行脚本依赖，或混入未批准/敏感文件均阻断候选通过；不得只跑一次普通 `git diff` 或仅见静态文件名就声称分发/提交完整。只有有权执行的真实打包/提交检查才能留下实际命令、退出值和真实消费者结果；
   - 未授权先记录 `unverified/blocked` 和待许可动作，不能自动 `git add -f` 或发布。见 `文件目录版本与跨会话恢复.md` 的具体库存记录。

## 必须拒绝的反例

- 存在 tests/ 就说已测试；CI running 被标 passed；flaky 重跑一次绿就覆盖失败史；Agent Eval 在用户dirty工作树写入后“恢复”用硬重置；HTTP文件生成当成功请求；模拟浏览器阅读当真实用户验收；只看 `git diff` 就宣称实际包包含 ignored/untracked 的必需资产；仅凭静态模型输出声称有真实多轮 Agent Eval 方差。



## Eval 与子任务证据的数据边界（SC-110）

规划 Agent Eval、子任务输入、事件/工具日志和证据交接时，先核用户/项目允许读取、存储和共享的具体数据范围；只提供验证本声明必需的文件片段与最小输入，排除无关私有源码、凭据、生产敏感数据和个人隐私。样本与日志按实际项目策略脱敏或使用获准测试数据；记录脱敏影响和无法提供的证据，不把替代样本当真实生产验证。合法本地读取不自动授权将原始资料发送外部模型/服务或公开日志。

原始证据存于当前任务获准的过程位置，明确真实版本、访问/共享范围及所需保留方式；
- 对外只交必要且已核准可共享的证据。
- 工具会读取超范围目录、自动上传敏感日志或无法满足必要隔离时不运行该 Eval，只暂停依赖结论并记 `unverified/blocked` 和精确补证/授权路径。
- 评测结束按已授权资源归属清理，不能以脱敏/清理为由改写真实失败历史或删除用户既有资料。
- 具体建议内容消费 `产物内容与自审契约.md`，任何真实运行仍需既有 E4 与宿主权限门禁。

## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 10.1 每项质量声明先设证据合同

每项需要验证的声明记录：`Claim ID / 来源 REQ 或 UC / 被测真实产物版本 / 前置环境与授权 / 推荐验证器 / 预期与失败条件 / 实际命令或步骤 / 原始结果与证据路径 / 结论状态 / 失效触发`。

- **D（确定性）**：路径/文件结构、解析、编号与引用、差异、Schema、单测/集成、包有效性；保留真实命令和退出结果。
- **A（Agent 行为评估）**：显式/意图触发、误触发、任务意图、角色视角质量、Skill 选择和审查/Auto 语义；在真实获准 Codex CLI 环境运行，事前冻结样例、评分细则和反例。模型主观自报只能是被评输入，不是裁判。
- **I（真实集成）**：目标 Codex 安装、文件系统、权限、真实请求/IDE、Web 文档站点、真实下游消费者/打包导出；无环境则 `unverified`，不能拿 D 冒充 I。
- **H（人工）**：产品范围取舍、新公开行为、受保护外部操作、通用规范生效、必需真人终验；脚本和 Agent 不能替代。

同一 Claim 可以同时要求 D 与 I（例如 `.http` 语法已生成 + 实际 HTTP 已执行），或 A 与 H（例如 Auto 行为解释 + 用户真实决定）；按适用性分别报告，不能取其中成功的一项代替全部。

**ABS-07 真实候选清单（仅提交/打包/发布时）**：生成现有项目文件的 `sourceInventory` 与获批需求/消费者派生的 `requiredDeliverableSet`，
 按 `realpath/path + version/hash + owner/sourceClause + working/staged/untracked/generated/ignored + requiredBy + includedInDeliverable(true|false|unknown) + packageOrCommitDestination +
actualConsumer + actualLoadedOrPackagedEvidence` 逐文件记录。
- 对没有 Git 的工程，各 Git 状态填 `N/A+reason`，仍要核实真实候选目录和文件消费面。
- 对 `ignored`、`generated` 不应自动包括所有文件：只把确属已批准交付义务的内容纳入；敏感/越权/过程证据应排除。
- 审查者须比较“必须交付的集合 ⊆ 实际授权候选集合 ⊆ 实际可消费包/提交结果”，以及候选中有无越权或未批准文件；
- 无权限生成真实包则只记计划检查 `unverified`，不得借压缩预览冒充宿主已加载。
- 若必需文件缺失、被意外排除、差异不明或候选改后未回归，暂停依赖交付；已有范围内修复并重新比较真实产物，真正新增范围才请求具体决定，之后才能声明相应 D/I 完成。

**真实工具选择**：验证计划在确定可用工具前先查当前仓库实际存在的脚本和测试资产（读配置、测试目录、命令风险、副作用与已有 CI 规则），优先复用经授权可运行的现成测试。
- 只有真实覆盖不足且本次已批准范围内确需补证时才规划最小补测；不得因喜欢某框架而安装新依赖。一个目标环境通过只能声称该环境下该版本该检查通过；
- 其他 OS/IDE/CLI/浏览器/HTTP 情境继续 `unverified`。所有用于审查证据的数字必须有真实源与版本并支持逐项追查，防止计数驱动结论。

### 10.2 质量状态与阻断矩阵

| 结果 | 使用条件 | 不允许的做法 |
|---|---|---|
| `passed` | 已按冻结的相应标准执行且有真实结果支持 | 只因文件存在、模型说通过或历史日志通过 |
| `failed` | 已执行且与预期不符 | 删除失败样例、修改断言/评分标准使通过 |
| `unverified` | 应验证但尚未执行或结果证据不足 | 写为 N/A/通过 |
| `N/A + reason` | 有充分事实表明此要求对当前项目不适用 | 用“没工具”或“时间紧”冒充不适用 |
| `blocked` | 必需验证无法完成、重大 Finding 或权限缺失 | 用人工确认报告准确性冒充对象质量通过 |

E4 仅实际授权真实宿主/浏览器/HTTP 交互产生。代码、README 和最终插件包必须在**被测试的有效版本**上保持一致；如生成后的包/依赖/文档改变，判定适用测试和审查证据失效。

**真实验证（E4）须在技能实际加载的环境中进行**：先把被测补丁按授权落到实际加载路径并刷新/重新加载技能，再在新会话中用会触发技能的真实意图提示测试；
- 被测会话须先证明已加载含补丁的技能版本（加载路径 + 实际文件 sha256，以文件证据为主、会话自报为辅），不能证明则该轮无效。
- 把规则正文塞给测试会话、代发或点明“这是测试”的结果只能记为“受干扰证据”，不得称为“真实验证”或 E4；未生效的候选不在任何会话的加载范围内，生效前只能得到受干扰证据。

**异步/Flaky 的拒收语义**：验证记录须区分 `not-started / running / completed-success / completed-failed / cancelled / unknown` 的**执行生命周期**与 `passed/failed/unverified/blocked/N/A` 的**验收裁决**。
- `running`/`unknown`/仅有局部 job 成功不进入整体 `passed`。
- 初次失败后偶然重跑成功需要保留全部失败史、环境/代码/测试版本、重跑原因和次数、被覆盖的断言/消费者，并按事前冻结的稳定性标准调查 flaky、环境、实现错误及 CI 状态；
- 必要稳定性/整体检查没有满足仍为 `unverified` 或 `blocked`，绝不选最后一次绿灯抹去失败。禁止调整断言、跳过/过度 Mock 或忽略子 job 来消除失败。

### 10.3 Agent 行为评测的最小可执行设计

**PoC-G Confirm/Auto 等价质量与效率比较**：在开始真实测试前冻结等价任务、仓库/依赖起点、宿主/模型版本、权限、同一 Required/Conditional 与 D/A/I/H 判据、失败注入与评估 Rubric。
- 分别保留可观察的 `human-confirmation-count`、可观察人工等待起止时间（不强行把用户离线时间算作插件性能）、模型/工具活跃处理耗时（若宿主可观测）、返工轮次、失败/重复样本、执行成本与结果；不可获取的指标记 `unverified`，不编造效率提升。
- **对 REQ-083 的确认效率效果**，在未来获得实际执行授权的可比任务中，将每次确认请求按 `Task/Artifact/Plan ID + 真实 SHA/版本 + Decision Scope + 授权来源及是否失效` 核对，
  区分 `same-effective-scope-redundant-prompt`（同一有效范围无新事实仍重复要求批准）与 `distinct-artifact-or-changed-scope-required-approval`（不同正式对象、新 SHA、计划实质失效或受保护决定）。
  - 比较只计算前者是否减少，后者不能当作可压缩的重复提示；
- 记录实际提示、决策和时间证据以及无可比样本/观察不全的限制，不能凭规则文字存在宣称已经提高效率。评价顺序**先满足相同质量与安全门禁，再比较效率**；
- 样本起点或环境不可比时报告失去可比性，不能挑选一次最佳输出或以少文档/少确认次数证明质量等价。

1. 先冻结一组以实际用户目标为输入的正反例，包括“未启用 Task Lifecycle 的普通编码问答”“引用 Auto 的 README”“错类 Bugfix”“部分确认”“两份同时待确认”“Skill 两候选冲突”“角色名称存在但检查为空”“编号匹配但正文引用旧版本”。
2. 在目标环境实际获得 CLI/工具授权后，记录当前客户端和模型/调用方式，按已确认版本使用 `codex exec` 或当前 CLI 确认支持的等价命令；功能参数从当时真实 `--help` 核实，不预写虚构支持矩阵。
3. 先固定评价 Rubric：不越权、阶段/范围正确、必需产物与自审记录完整、真实使用者可执行、证据正确与失败处理。开放性评分需人工或可信独立评估步骤；模型自评不得独立判定完成。
4. 保存输入、输出、可获得的事件/工具结果、失败样本、评分规则版本、成本/时间及重复采样依据；
   - 不因模型非确定性挑选一次最好结果。
   - **ABS-11/AC-110：**当评价 Agent/模型非确定性且有真实可比较的重复采样时，按冻结 Rubric、相同任务/宿主/模型/配置分别保存每次输入与得分/判定、成功/失败总数及类型、误判样本、总样本数、执行成本和适用的**结果分布/波动/样本方差或范围**，写明比较方法、限制和异常值，不删除失败样本。数值方差只在有可比较的数值度量和足够样本时计算；
   - 样本不足、环境差异不可比或缺事件数据时明确 `variance=N/A|unverified + reason`，不得编造标准差/成功率，也不得拿一次最佳样本证明达到稳定性门禁。
   - 是否需要重复采样按已批准风险、成本与评分判据决定，**不为普通确定性单测强制多跑**。
5. 变更 Skill 正文、Reference 或测试环境后，重新核实哪些样本失效；未测的宿主功能明确 `unverified`。

**Agent Eval 安全隔离**：在实施阶段首次使用真实 CLI/子 Agent Eval 前，依据实际工具权限及任务范围核实是否有受控沙箱/隔离目录或合法 worktree，并记录原用户工作树 HEAD/dirty/untracked、预计读取/写入面、依赖启动脚本和临时进程/端口、外部网络/服务、副作用及预期清理。
- 可在无危险副作用的许可范围内选择独立临时工程副本、受控测试环境或只读 Eval；
- 不能安全隔离且测试可能改写/清理用户工作树、生产数据或共享资源时 **不执行**，保留 E4 `unverified` 及补证/授权路径。评测后复查文件/Git/临时资源和受测对象版本；
- 发生污染、未知副作用或出乎授权的写入时记录真实 `failed/blocked`、停止受影响后续检查，并仅在确认归属及具体许可后恢复，**不得自行 `git reset --hard`、删除用户未提交文件或杀未知进程**。E3 的本文协议不等于已在真实宿主跑过 Eval。

### 10.3.1 Codex CLI 执行权限与 Task Lifecycle Auto 严格分离

`codex exec --full-auto`（仅在当前真实 CLI 版本支持该参数时使用）是 **Codex 宿主的执行/批准策略选项**，不能作为 Task Lifecycle 已获得 `Mode: Auto` 的证据；
- 其他宿主的自动执行/免确认模式同理。
- 反之，任务级 Auto 也不能自行选择更宽的 CLI 权限或直接执行敏感文件/网络操作。Agent Eval 样例应记录两个维度各自的真实来源及适用范围；
- 当 CLI 命令、宿主权限或合法任务 Auto 的一方不明时，不能将另一方推断为已授权。

### 10.4 Reviewer 独立性与能力不足

审查时按真实宿主能力优先使用独立 Review 上下文及同一冻结标准；不可用时同一上下文进行生成/审核分离、反向遗漏扫描和真实证据核对，并标注审查方式。必须的独立证据缺失时保留阻断，不以角色扮演证明独立性。没有专业 Skill 并不自动阻断；判断实际所需专业能力和可靠替代验证，仍无法补足则局部暂停并登记真实 Gap。

### 10.5 真实进度、验收追踪和证据等级分离

**证据等级（主定义）**：E1=已批准源文本可回查、E2=相关现行规范、E3=当前真实文件/静态检查、E4=当前真实宿主/HTTP/浏览器/Agent Eval/人员行动。

**审查与验证方式**：审查记录、审查报告、验证结论、收尾报告与晋升报告逐项标明方式：静态审查（只读文本推演，写明所读文件或快照）、
自动化检查（写明所跑门禁/测试及结果）、真实运行（写明宿主/会话、用例与次数）。只做静态审查或自动化检查的，写明“未真实运行”，不得写成“已验证行为”或“实测通过”；缺方式的结论视为不完整。

**每次实质性受管回复**（末尾附 SKILL.md §4 的 4 行进度卡）：先说明当前可证结论，再给与实际状态贴合的下一步。
- 已有有效授权且可继续时说明接下来的动作并直接推进；需用户决定时列准确事项、推荐取舍与影响；阻断时给所缺证据/权限和恢复路径；完成时交付结果与剩余限制即可自然结束。适用于澄清、方案说明、执行进度、失败和交付；简单礼貌确认免机械尾段。
- 交付或引用需用户阅读的文件时，以宿主聊天中可直接点开的形式发送（优先附件，也可用可直接点开的文件链接），可同时附路径；不含凭据等不宜外发内容；宿主不能直接点开时说明原因并给出路径。
  - **报告类产物与 Grok Bot 阅读版 Page**（审查报告、方案、契约草案；.md 为正本，宿主为 Grok Bot 时另做 Page）：
    - **报告类产物（范围定义）**：审查报告、方案（含提案）、契约文档三类；其余产物不属报告类，篇幅大小不影响归类。
    - **方案的定义**：交给用户审阅或批准的技术方案、实施方案、修复方案、审查方案和候选提案正文；对话里随口给出的选项说明、单张决定卡片不算方案。
    - **契约文档的定义**：只算待批准的契约草案，即使用契约、接口、参数、配置格式和输出协议的草案；仓库中已定稿的契约不做 Page。
    - 第 1 条 **正本**：报告类产物默认只产出 .md；.md 始终是正本，入库、diff、审查（含 Codex 审查）和批准都只认 .md 及其 SHA。
    - 第 2 条 **Grok Bot 宿主**：当前宿主为 Grok Bot、且本会话直接面向用户交付时，在 .md 之外再做一个 Page（Canvas）供阅读；Page 不是批准对象，与 .md 冲突时以 .md 为准。被派发会话（无用户可见渠道，含 SKILL.md §0「接收方门禁」下的会话）不做 Page，只把 .md 交回派发方，不因缺 Page 视为交付未完；
      由面向用户的会话负责做 Page。
    - 第 3 条 **宿主中立**：Codex、Cursor 等无 Page 能力的宿主只给 .md（按本文件「每次实质性受管回复」下「交付或引用需用户阅读的文件」句发送），不虚构 Page，也不因缺 Page 视为交付未完。
    - 第 4 条 **Page 标源与复用**：Page 最上方一行标明来源 .md 的路径和 sha256（页面顺序：来源行 → 顶部目录 → 正文，正文第一节按 10a）；.md 更新时修改同一个 Page 并更新 sha256，不新建。
    - 第 5 条 **做 Page 的范围**：报告类产物（审查报告、方案、契约文档）不论篇幅都做 Page；非报告类产物（CHANGELOG、配置说明及其他产物）只给 .md；篇幅长短不改变归类（同范围定义）。
    - 第 6 条 **单文件 HTML 按需**：需要跨宿主或本地阅读时，按需生成自包含的单文件 HTML，不作为默认；只在用户明确要求时生成，任何宿主相同，未要求时不出。
    - 第 7 条 **Page 目录（仅 Grok Bot 宿主）**：所有报告类 Page 顶部始终显示一份目录，每节标题旁有返回顶部目录的「↑ 目录」链接，不论篇幅（这两项用章节锚点＋文字链接写出，必做）。验收看阅读效果：目录始终可达、不随正文滚走，宽窗口下可常驻在正文旁，窄窗口下不挤占正文。
      **组件/宿主默认满足即可，不手写 fixed/观察器/像素计算**：侧栏、抽屉、当前章节高亮由宿主或组件提供时直接用，不提供时只保留顶部目录＋「↑ 目录」，不因此视为不合规。参考实测值（非实现义务）：窗口 ≥ 968px 时侧栏 top 96px、left 24px、宽 200px，正文让出 248px。
    - 第 8 条 **Page 正文宽度（仅 Grok Bot 宿主）**：验收看阅读效果：正文不过窄、不过宽，在可用空间里居中，表格和流程图随正文同宽；可用宽度不足时铺满。组件/宿主默认满足即可，不手写 fixed/观察器/像素计算；套件宽度选项（column、wide、full）中选最接近该效果的一档即可。参考实测值（非实现义务）：正文最宽约 960px。
    - 第 9 条 **已知限制与保底（公开链接）**：pages.grok.bot 公开链接把 Page 嵌在与内容等高的 iframe 中、由外层页面滚动，fixed、sticky 与 IntersectionObserver 跟随均不生效；
      因此公开链接下不显示任何悬浮目录元素（左侧目录、按钮、抽屉都隐藏），只用常显的顶部目录＋每节「↑ 目录」。外层页面不限宽，视口 ≥ 960px 时容器实测正好 960px，视口不足 960px 时按第 8 条铺满；公开链接下不加侧栏、不加 padding。
      正文字体（15px、不加字距、中文字体以微软雅黑、苹方开头）仅在 v0.15 Page 试用，不属本条规则。
    - 第 10 条 **Page 按内容生成（仅 Grok Bot 宿主）**：Page 不套固定模板，按内容选最适合人阅读的呈现方式。细则（每条附理由）：
      - 10a正文第一节是结论与待决事项（位于来源行和顶部目录之后），长细节默认折叠。理由：先回答“要我做什么”，细节按需展开。
      - 10b顶部目录与「↑ 目录」始终保留（第 7 条）；不因篇幅或章节数增减目录；应用内侧栏或抽屉按第 7 条交给组件/宿主默认。理由：目录始终可用，悬浮形态不由 Agent 手写。
      - 10c流程用流程图，节点内只写短编号，图后紧跟“编号—说明”表。理由：节点长文字会挤压变形，表格可读又可检。
      - 10d对比用表格；风险、阻断用颜色标出，并同时带文字标签。理由：表格便于横向比，颜色加文字不依赖色觉。
      - 10e表格单元格字距为 0、表格与流程图随正文同宽。理由：v0.15 实践中可读性更好，属实现细节。
      - 判据：同一内容若含流程/对比/待决事项，Page 中分别以 10c/10d/10a 的形式出现；无对应内容时不强行添加。
    - 第 11 条 **交付自检（仅 Grok Bot 面向用户）**：本会话直接面向用户交付报告类产物时，在宣称「已交付」之前须已写出 Page，且用户可见回复含可点开的 Page 链接（或 WriteCanvas 成功 url）；命中须做 Page 却无链接/无 Page → 拒收该次交付声明，先补做再交付。
      例外仍按第 2～5 条（被派发、非 Grok Bot、非报告类、已定稿契约不做 Page）。
    - 第 12 条 **流程型 Page 版式（仅 Grok Bot 宿主）**：在已按第 1～5、11 条决定做 Page 的前提下，若读者要「顺着门走、并查下一跳和依据」，用本条版式；若读者要「看结论、找问题、批一稿」，不用本条。
      本条管怎么排，不改第 1～5 条「要不要做 Page」（与 CAND-20261026-009 分层）。第 4 条标源与复用（来源行、sha256、同页更新）仍遵守。
      - **适用**：流程门禁、分叉多、要对照执行的内容——含派发/审查/复审主路径、Feature/Bugfix/Docs 阶段门禁总览、接力或委派「触发→步骤→停点」、实施计划里依赖多且有分叉的 WI 图；混装方案/计划**仅**门禁/分叉/对照执行的流程段用本条，其余章节保持原版式。
      - **不适用**：审查/复审/核实报告（结论先行＋Finding 表）；决定记录、晋级记录、ACTIVATE（短事实时间线）；待批契约稿（按契约章节）；验证报告与抽测结果（证据与用例表）；候选正文、diff、会议纪要、进度一句回复（.md 或聊天即可）。
      - **版式**：阶段总览图＋编号 Steps（正本有材料/停点则写入，无则省略）＋逐步表（步骤/动作/详细描述/实现方式/流转/依据，每个编号子步一行，行序同 Steps）；
        多阶段可加阶段 tab，附录用二级 tab，阶段 tab 与附录二级 tab 同构（图＋Steps＋逐步表）；总览 tab 只放总览图与 Steps，不放全路径逐步表。

        Steps 每步对应一个图中节点（标题＝编号＋摘要），下挂编号子步 1. 2. 3. 与一行浅色「材料：…」，停点只在子步未覆盖时补一行「停点：…」；不得把材料、结果、停点等字段拆成步。
        流转列须列出正本已有的例外回流（写成「例外：…」），不编造新边；实现方式或依据未在正本或规则写明的标「未写明」，不许编。

    - 第 13 条（已撤回，CAND-20261027-013，t719u：Page 只由 Grok Bot 生成并由 Rocky 验收，本条多一停点无新增证据；命中三类按 §7.10 第 7 条原条款）。

      第三方会话的产出不算 Page，也不算 Page 真实生成证据。§7.10 第 7 条所说的 Page 真实生成按本条执行。

### 10.6 Bugfix 回归与代码维护质量的验证设计

| 检查声明 | 适用验证器 | 预先冻结和真实完成证据 | 失败处理 |
|---|---|---|---|
| 原 Bug A 确实解决 | D 单元/契约/集成；必要 I 真实 API；条件 A | 修前失败样例、修后同输入同版本真实结果 | `failed/unverified` 不关闭 |
| 其他合法行为不受破坏 | 根据共享消费者分流 D/I/H | 原有合法值/默认/错误语义，真实消费者调用与回归结果 | 原行为被破坏归新回归，原任务阻断 |
| 本次引入的 B 已修复 | 真实因果分析 + D/I/必要人工 | 关联 Finding、真实代码 diff、A+B+适用影响面复证 | 未完成必要复证不关闭原 A |
| 根因与修复质量合格 | 代码审查+客观检查+适用独立视角 | 实际源码与项目约定、复杂度/重复实现/异常路径/可测试性审查 | 高风险质量缺陷 P0/P1 阻断；风格建议可非阻断 |
| 测试没被篡改以凑通过 | D 对测试 diff/冻结预期核查 | 原始断言、覆盖声明、实际执行，避免过度 Mock | 修复/测试须回到有效标准后复证 |

- 对受管 Feature 的代码修订和 Bugfix 返修消费同一质量护栏；对纯 Docs 的文档编辑按真实风险 N/A。不设固定 100% 覆盖率、函数行数上限或无依据全仓回归。
- PoC-J 在获授权的目标环境用受控样本验证 A→B 的真实回归、合法返修及维护性 Finding；未执行 PoC/宿主能力时 E4 保持 `unverified`。

**对 Bugfix/Feature 实际测试的补强**：影响面必要验证必须对应相同真实代码/依赖/CI 完成状态，记录失败→调查→重跑→最终判定的连续证据，flaky 未排除和 CI running 时不能提前关闭原 Bug/新回归；与已获批行为保持矩阵一起回读。只读设计阶段 E3 可检查上述合同，不能虚构已真实跑完回归。

### 10.7 分层回归、证据复用与重跑依据

消费`正式专项审查与Finding.md` §7.9的固定发现轮次与修复批次。在既有验证计划/记录中确定每层适用集合和失败条件，复用项目真实可用的脚本与证据，不新增固定覆盖率或强制重复次数：

| 层次 | 适用范围与时机 | 必须保留的证据 |
|---|---|---|
| 每项最小验证 | 每项修复后确认原失败及紧邻不变量；可在批次内执行 | 原失败输入/断言、修订版本、实际结果；不以局部通过关闭其他Finding |
| 批次影响面回归 | 一批有关联修复完成，核查直接/间接消费者、共享契约、原正确行为及新回归 | 真实diff与依赖理由、适用检查集合、各Finding结果；共享契约影响广时据证扩大至必要整体回归 |
| 最终适用验收 | 集中修复后，对确切交付候选统一核对全部必需通过条件 | 当前结果与有据复用证据的完整集合、候选指纹、未验证/失败和必要人决；统一验收不等于全部命令重新运行 |

**每次重跑先说明依据**：实际改动/新事实及对象版本 → 哪些旧证据为何失效 → 受影响条件/消费者 → 拟执行检查与可复用结果 → 本次期望新增信息。没有新增事实且同法重试无实质进展，执行审查Reference §7.6，不盲目重跑。若静态证据足以裁决一个静态事实，不得仅为取得绿色CLI退出而重新执行整条Agent流程；必要真实运行仍不可由静态检查代替。

**证据复用条件**：核实被测代码、相关契约、消费者、依赖/环境、测试/评分标准、执行状态与本次声明的适用性；
- 无相关变化且原证据完整时可以引用，保留原版本/Hash/执行者，不能把历史结果改标为新版重新测试。
- 仅报告改名、无语义格式或证据文件扩展名纠正，核对其真实内容、可读性和引用，不自动使产品行为证据失效；若涉及实际内容、加载入口、解析器、环境或消费者变化，须重新判断影响。
- 无法确定时将该声明列为`unverified`并最小补证，不能推测全部有效或全部失效。

**失败与最终退出**：所有失败、取消、中断、flaky调查和纠正均保留；产品缺陷与测试/环境/证据包装错误分别裁决。新修复影响了既有结论时补跑必要范围，不能承诺最终验收永远只运行一次，也不能每次从头重启全部阶段。最终必要条件未满足时保持相应阻断；任务Auto不替代独立授权、真实宿主证据或最终真人验收。
