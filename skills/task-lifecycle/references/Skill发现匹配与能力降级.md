# Skill发现匹配与能力降级

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：已批准任务中的当前专业声明找不到足够能力，或用户明确指定/询问某项专业 Skill 时。

**唯一主责**：真实可用 Skill 主辅选型、可信来源硬准入、失效降级及 Gap 的合法用户可见处置

**直接消费者**：按需的阶段角色/专项审查、失效降级、通用 Gap 登记。

**联动 Reference**：`角色与专业审查.md`、`通用规范吸纳与自我进化.md`。

## 适用时逐项执行

1. 先看当前真实宿主中**已安装/可用**的 Skill、项目既有规范、工具与基于证据的审查能力；满足必要标准就复用，不因名称不同反复联网。
2. 不足时在合法联网许可与宿主现有能力下搜索**可信官方目录**；记录发现来源、发布者、版本、真实安装/加载支持证据。目录由官方提供≠条目由官方开发；发现≠安装≠加载。
3. 候选先过硬门槛：项目/宿主兼容、实际必要角色/声明、可信来源、额外权限和安全、冲突与许可证/限制。再依据项目语言/任务成本与必要验证质量选最小主 Skill，必要时增加职责不冲突的辅助。
4. 若没有专业 Skill 但可用同等检查方式，诚实说明降级；若对关键质量必需但无能力/权限，仅阻断受影响节点，提出精准补证/审核/安装提案，不能假通过。
5. 根据真实 `whatFailed / whyMissed / candidateVersions / checkedSources / affectedGate / fallback` 记录 Gap；某次任务特殊情况不自动升为通用 Skill。
   **Gap 归因门禁（REQ-019/031/033）**：逐案区分 `invocation-gap`（已有 Skill/规则未被正确发现、触发或加载）、`rule-gap`（证据证明实际缺少可执行的通用检查规则）、`specialist-skill-gap`（确实需要而当前宿主不可用的独立专业 Skill）及 `tool-or-environment-gap`（缺工具、权限、网络、环境或可观察执行证据）；证据不足标 `classification-unverified` 而非硬选 `rule-gap`。先核实已安装 Skill、实际调用与当前规则、权限和替代验证器；前两类不能靠安装新插件代替根因修复，后两类不自动变成通用规范。仅真实 `rule-gap` 经通用性资格检查才可提出进化候选，其他按调用修复、维护建议或补证/局部阻断处理。

6. 如果后来确需新 Skill/升级/安装，只提出独立维护建议，待用户与宿主实际授权，不能自动写入 DevCodex 或插件目录。

## 必须拒绝的反例

- 在官方目录检索到了 Skill 即表示已安装可用；未经用户同意自动下载/运行第三方 Skill；借“安全审查”运行陌生命令；必需专业核验做不了仍标 passed；一次性缺口被自动作为 active 规则。



## 独立 Skill 维护建议的最低信息（REQ-041）

确有专业能力缺口时，独立维护建议按 `产物内容与自审契约.md` 的建议最低信息填写：当前真实证据与现有能力为何不足、所需检查/工具及预期收益、适用与不适用情境、可复用规则或已有 Skill 的替代、引入/执行/长期维护成本和风险、不采纳后果、影响门禁与精确待决事项。没有可靠成本/兼容证据则标未知。建议可与合法替代审查并存，但不能因写了提案就创建/安装 Skill、修改 DevCodex 或宣称缺口已解决；维护实施仍是独立授权任务。

## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 8.1 角色、Skill 与执行者是三种不同概念

- **角色**：描述从哪一类消费者或专业责任视角提出检查问题。
- **Skill**：提供可能的专业规则/工具使用方法，只有确实可读取、可使用时才是可用能力。
- **执行者**：当前模型、真实受授权子 Agent/Reviewer、实际工具或真人；模拟角色不等于真实独立执行或专业资质。

不能因为提出了“架构师/安全工程师”角色就自动安装或创建同名 Skill，也不能因为发现 Skill 便跳过本插件的审批、证据与工具权限。

### 8.2 同类 Skill 的按需发现与竞争选择

```text
当前阶段的必要角色/质量声明与真实项目事实
  -> 核查当前已安装的 Skill / 项目规范 / Reference / 工具
  -> 若必要能力足够：直接使用，不为同名 Skill 再联网
  -> 不足：按宿主和网络许可，在可信官方目录按需发现候选
  -> 硬性准入过滤：实际宿主可用、源可信、所需权限受允许、版本适配、满足必要检查
  -> 剩余候选按当前技术栈/用户目标/任务成本/验证质量选择主 Skill
  -> 若需互补：按需增加不冲突的辅助 Skill，说明各自职责
  -> 能力/证据仍不足：合法降级 + 局部阻断 + Gap 记录
```

官方目录里的条目可能由第三方发布，**目录归属不等于官方开发或自动可信**。用户当前已指定的 Skill 在满足安全与质量硬性门槛后应优先考虑；不兼容或越权不能勉强执行。候选间规则冲突时以已确认需求/使用契约/内置核心规范为准，其余需要事实核查，产品性取舍交真实用户。

**推荐的简洁选择记录**：当前任务/阶段与能力声明、候选名称和版本、实际安装/加载证据、准入失败理由、选中主 Skill、辅助 Skill、排除和冲突、额外工具权限、实际使用/未使用与质量结果。该记录可并入当前审查计划，不新增专用调度数据表。

### 8.3 无 Skill 或技能失效时

| 情况 | 合法降级 |
|---|---|
| 无同名 Skill，但有可靠现有规范和可执行验证器 | 直接开展动态审查；记录实际方法，不登记虚假缺口 |
| 官方目录无法访问 | `discovery-unverified` 而非“官方不存在”；回退现有工具/规则 |
| 已有 Skill 未触发/加载失败 | 记录真实能力使用缺陷，先修触发或加载事实，不立即新建 Skill |
| 专业 Skill 缺失但不影响必需质量结论 | 使用可靠替代审查并说明限制；可按证据登记能力改进 |
| 必须的专业能力/工具/权限均不足 | 只阻断受影响质量门禁，精确提出所需资料、授权或专家复核 |
| 某 Skill 要求安装、运行代码或联网 | 用户/宿主明确允许后才执行；不把发现等同安装授权 |

### 8.4 Gap 记录和长期处理

可优先写在当前《审查报告》或《任务交接说明》中，字段至少包括 `Gap ID/目标专业能力/候选核查/具体失败证据/当前审查降级/影响和阻断/推荐补足路径/状态`。在多任务确认有复用价值时可按需建立工作区外置《能力缺口索引.md》，**不等于 `evolution/INDEX.md`，不会被当成 active 规则加载**。

处置分流：项目一次性差异留当前任务；已有通用 Reference 不足可提出修订；已有 Skill 用法/触发失败优先修复；真正需要新专业 Skill/工具时形成维护建议，经用户或维护者另行立项，再按授权开发/安装/验证。不能从当前审查的 Gap 自动创建原生 Skill、插件或向 DevCodex 推送。
