# Docs受众与站点质量

> 此文件是 Task Lifecycle V1 **执行规则**，不是新的需求审批、实际运行记录或额外 API。根依据为用户正式批准的开发需求 V0.18-R2、Usage Contract V0.5-R2 与技术方案 R9-R2。不得以本文覆盖更高优先级的真实用户决定或宿主安全权限。

## 读取条件与职责

**触发**：Docs 任务有实际用户页面、既有站点，或Feature/Bugfix交付涉及README/API文档/公开使用行为时。

**唯一主责**：G-DOC-01～05 和真实用户任务、源码/发布一致、公开与内部文档隔离

**直接消费者**：DOC03/DOC06/DOC07/DOC09、Feature交付公开契约、HTTP示例。

**联动 Reference**：`Docs流程.md`、`验证与证据分流.md`、`HTTP辅助验证.md`。

## 适用时逐项执行

1. 明确使用者、集成者、维护者、内部运营等真实读者以及公开/内部界限，分别确认目标和可测任务；公开 API Reference 可以技术细，但不能用内部流程日志淹没 Quick Start。
2. 以正式契约→真实当前源码/包/API/CLI→文档页面/示例→实际发布版本逐项核查；任何新默认值、错误码/字段必须有真实依据，不能从文档推断可用接口。
3. 现有站点且任务触发时按 G-DOC-01 事实、02信息架构、03首次成功/查API/排错任务、04真实build/页面/导航/链接、05适用专项（版本/语言/键盘/SEO等）逐项选验证方式和原始证据。
4. DOC07 对读者路径的真实环境执行与用户体验做适用验证；静态build只能证明对应命令执行，不能证明真实用户能完成目标。真实浏览器/相关宿主不可用时保留 unverified 并按必要质量门禁阻断。
5. 只有README且无站点要求时，站点检查 `N/A+reason`；不要为满足模板新建站点/改框架。内部审批日志、客户秘密和测试凭证不得进入公开页面。
6. 改变公开产品行为时停止 Docs 越界动作，形成建议或合法 Feature/Bugfix 任务，经真实用户批准。

## 必须拒绝的反例

- 只看导航标题就说首次成功；页面可build但实际用户点不动；未获批准而新建文档站点；公开 Quick Start 复制内部 Task 风险记录/凭据；Docs修改不存在的SDK API实现。



## 已批准技术基线的具体约束（按需回读）

以下为获批准技术方案的**规范性设计约束**摘录；标题中的旧版本称谓不代表当次项目已通过真实测试。其内容应按当前真实任务、授权与触发条件消费；若与本文件摘要不一致，以已批准技术基线为准，不自动扩大范围。

### 12.1 Docs 文档类型和源—消费者一致性

Docs 输入按受众与目的区分：使用者入门/教程、公开 API/SDK/CLI Reference、贡献维护者、内部接口、运维发布、受管内部过程。公开页面只能承诺**真实批准且实际可消费的功能**，必须能从当前真实源码/包导出/CLI 或已批准外部契约回溯。项目内部架构、构建和审查日志不能因为都是技术材料就塞进 Quick Start；但公开 SDK 使用者需要技术参数与返回类型，不能笼统删除。

设计从 canonical 接口来源开始核实：`当前已确认公开契约 → 真实 API/导出/CLI/消费者 → 用户实际页面/示例 → 实际发布版本`。Doc-only 不得为解释不存在的 API 擅自修改业务代码；需要修 Bug/新增能力时提出独立 A/B 变更。历史复制页面、生成副本、不同语言版本须识别实际源与最终消费，不能只查单个 md 文件。

### 12.2 Docs Site Quality Gate（存在站点且适用时）

| 门禁 | 当前必要验证 | 真实失败与处理 |
|---|---|---|
| G-DOC-01 事实 | 公开文档声称的 API/默认值/错误/示例对照真实消费者与已确认契约 | 文档编造接口、旧版本误用 → 退 DOC05/DOC06，必要上游变更 |
| G-DOC-02 受众/信息架构 | 首次/集成/维护者读者目标及真实导航、搜索可发现性（若存在） | Quick Start 被内部流程淹没 → 内容结构修订 |
| G-DOC-03 读者任务 | DOC03 冻结适用的“首次成功/查 API/排错”代表性步骤与成功条件，DOC07 真实执行/访问 | 只有标题存在却不能完成任务 → 失败，不写 passed |
| G-DOC-04 真实站点 | 实际 docs build、页面渲染、链接/锚点/路由、适用移动/键盘交互 | 仅 build 成功、浏览器打不开 → 必需 I 验证未完成 |
| G-DOC-05 专项条件 | 版本、语言、SEO、搜索、性能、完整无障碍等按真实目标/风险触发 | 缺浏览器/工具时 `unverified`，并按冻结通过标准决定是否阻断 |

站点不存在且当前任务仅修 README 时站点检查 `N/A + reason`；不能以改善质量为由擅自安装网站生成器。使用 Playwright/Lighthouse/link checker 等已有合法工具时要看项目是否已有依赖与权限；工具名是**可选择的验证手段**，不是所有项目都必须引入的新依赖或一组虚构必备插件。高风险公开站点真实用户可理解性不能由模型模拟独立证明。
