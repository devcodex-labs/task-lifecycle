# 示例：Bug A 修复引入新回归 B（演示，不是真实修复证据）

> 以下 A/B 是虚构标签，不涉及实际生产数据或真实测试通过。

用户已明确启用受管 Bugfix，模式 Confirm、合法深度已选、项目及路径已安全绑定。

1. B01/B02：基于真实批准的预期行为与可重现事实提出 Bug A；同时记录共享消费者 `consumer-X`、合法正常行为不变量、实际环境是否可执行。
2. B03：最小修复方案必须覆盖对原 A 的正向恢复与 consumer-X 的原正确行为保持；如公开行为或字段要改变，必须单独请求产品决定。
3. B04/B05：只有当前写权和安全 Git dirty 核验后才改源码；保持真实 diff/原始失败历史/专业审查 Finding。
4. B06：若实际新异常 B **有证据证明由本次修复引入**，分类 `introduced-regression`，建立与 A 关联的 Finding，阻断 B07/B09，**在同一原修复质量闭环返修**。
5. 修 B 后须在相同当前版本复证 A+B+consumer-X；检查没有通过吞错、删除测试或放松原断言造假。
6. 若 B 原本已存在但本次暴露或因果不明，分别写 `pre-existing-exposed/causality-unverified` 和补证步骤，不因为同一时间发生就断言修复引入。
7. 最终 B09 报告展示原 Bug、真正原因、修改差异、回归/未测和用户待确认情况；不能仅凭自审报告宣称已完成。

**反例**：B 被分拆成一个没人授权的新工单，原任务 A 单测绿便宣布关闭 —— **必须拒绝**。
