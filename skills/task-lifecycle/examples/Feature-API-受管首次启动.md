# 示例：HTTP API Feature 的合法受管启动（演示，不是真实项目/E4）

> 这是**虚构交互说明**，不得将示例的用户决定、文件路径或测试结果复用到真实任务。示例只表达如何运用已批准的流程，不定义新公开 API。

**可信当前用户**：“给当前项目新增一个查询接口，先规划，不要修改源码。”

**受管入口 00 的合法响应**：

1. 读取当前用户允许的项目路径、现有 API/Schema 和 Git dirty，真实不具备工具时标 `unknown`，先不写任务文件。
2. 分类 Feature；默认 Confirm；记录源码写入尚未授权。
3. 用户没有选择 `workflowDepth`，展示 `fast/standard/thorough/custom` 四档及基于实际接口风险的推荐；**不直接选中 standard**。
4. 用户明确选 `standard` 并授权在经过真实安全检查的仓库外目录写入过程文档后，才生成当前《任务描述》和《任务工作流方案》候选，自审并按确认记录合法生效。
5. A01 审定公开目标 → A02 Usage Contract（真实 API、字段域、缺省/错误/权限、正反场景）→ A03 技术设计 → A04 Work Item 规划。期间即使发现更好的缓存方案，也先写 `suggested-unapproved`，不自动纳入。
6. `.http` 默认 `suggest`：仅介绍可生成的样例和风险，不直接写 `.http`；用户明确选择 `generate` 且授予相应源码写入权时才创建变量化文件。
7. 代码验证与实际 HTTP 请求分别需要真实环境许可，未执行分别标 `unverified`；即使 `.http` 成功生成，也不宣称接口测试通过。

**应拒绝**：README 暗示开启 Auto、没有用户选档就写入、API 还没确认就新增 SDK 方法、生成 `.http` 就宣称真实执行、在项目 Git 内建立内部审查报告。

## CLI 使用面的不同契约示例（虚构，未执行）

以下假定用户自己的项目已存在一个文件校验 CLI；这不是 Task Lifecycle 提供的新命令，也不假定任何真实工具拥有某个参数。

1. 可信用户明确：“给这个已有 CLI 增加已讨论的输出格式选择，先规划，不改源码。”先读取真实命令入口、帮助/参数解析、退出码、stdout/stderr、现有消费者和测试及 Git dirty；不能访问时如实未验证。
2. 入口分类 Feature、默认 Confirm；没有合法选档则展示四档。用户明确选择 standard，并授权已核实安全的仓库外过程目录后，生成并自审《任务描述》《任务工作流方案》，按准确对象取得确认。
3. A01/A02 先核原文本输出兼容、可接受输入、格式选择的真实参数形式/默认、缺省与非法值、成功/失败退出码、输出流和脚本消费者；不得猜测现存参数名或直接新增公开承诺。形成使用契约候选及专项计划/报告，按模式确认后才进技术/实施计划。
4. 当前仅规划未授权写源码。取得准确实现授权后，A05 才改命令消费者与必要测试；应验证旧调用保持、获批新格式、非法格式/缺文件、管道消费和错误流等适用条件。没有 HTTP 面时 `.http` 为 `N/A+reason`，不造请求文件。
5. 必须拒收：只看 `--help` 文本就说行为兼容、为便利改变退出码、删除旧输出断言、把示例中的标准模式当真实用户选档、借代码批次确认执行 commit/push。必需CLI实测未完成保持 `unverified`，不能称首次成功。

## 同一Feature的A05～A09收尾（虚构条件路径，未执行）

**后续条件**：真实任务的A01～A04已按当前合法模式生效，用户另行授予准确源码写入及适用验证许可，才可进入下表；最初“先规划，不要修改源码”的要求本身不授权实施。下表描述应如何收尾，不表示本示例已获得批准、修改或通过测试。

| 阶段 | 输入与应做的动作 | 退出、失败与未测边界 |
|---|---|---|
| A05 实施/代码审查 | 回读有效REQ/UC/WI和当前源/dirty；在允许写集中实现，集中发现/按根因修复，核真实diff与消费者 | 交付准确源码/候选身份和审查证据；未授权写入或必要Finding未解决则停相关链；HTTP生成/请求仍各按许可 |
| A06 验证 | 按冻结的正常/拒收判据记录实际命令或动作、预期/实际、版本、环境、原始证据与退出码 | 计划、已跑通过、失败、未测和有理由N/A分别记录。本例无真实结果，状态仍unverified；必要测试缺证不能批准依赖其通过的交付 |
| A07 交付审查 | 必需验证满足后，给完整候选入口、文件集合、真实Diff/SHA、说明和未覆盖范围；核实际消费文件 | 当前包必须对应被审/被测版本。产出ZIP不证明已安装；改候选后只失效相关证据并补复核，不重标历史结果 |
| A08 条件发布 | 若真实任务没有发布意图，记N/A及理由；有新请求则先核准确目标和独立许可 | 不因Auto、交付确认或ZIP存在而commit/push、更新账户、安装或发布；未知发布结果先观察，不盲重放 |
| A09 完成/反馈 | 交接最终版本、实际完成与未测、剩余风险、回退入口及下一动作；记录真实用户终验是否存在 | 技术就绪与真人验收分别记录；无真人事件就保持待验收。A10可在任意阶段因实质变化插入，不是必跑末步 |

### 可复用用例结构与简短rubric

将这个结构用于真实任务时，填写实际输入、当前REQ/UC/WI、候选版本/可计算SHA、授权和环境；先冻结预期与拒收，再分别填实际结果/原始证据入口或未测原因。本例这些实际执行字段均为未执行，不提供虚构Hash或批准。

| 判据 | 正向与拒收条件 | 本例证据状态 |
|---|---|---|
| 候选与输入一致 | 实际消费者、源/包和有效上游版本一致；旧结果不能冒充新候选通过 | unverified，只有演示 |
| 验证事实可追溯 | 每条预期对应实际命令/输出/退出码和证据；只有计划、文件存在或模型自评不算通过 | unverified，无真实命令 |
| 修复和复用有依据 | 原失败保留，同根修复后逐项复验；未变消费者有据复用，不盲重跑全流程 | unverified，未实际修复 |
| 交付、发布、终验分开 | 当前候选可读；无许可不发布，无真实用户决定不填human-confirmed | 未发生真实发布或终验 |

实际D/A/I/H、隔离及证据新鲜度按[验证与证据分流](../references/验证与证据分流.md)；回归责任参见[既有Bugfix示例](Bugfix-A引出B-同责任回归.md)，文档/站点分流参见[既有Docs示例](Docs-README与现有站点分流.md)。复用历史行为证据须保留原候选/环境、适用条件和未覆盖风险，不复制私人日志进包或默认追加模型运行。本示例和rubric不替代真实E4，也不是新的评测框架。
