# 示例：Docs-only 修正错误 README（演示，不是站点验证证据）

用户（按意图触发，未点名插件）：“帮我修正文档里的安装说明，**不改业务代码，不发布**。”

- `00`：有限规则自举并输出预检查后，只读核 README、真实项目、包/版本和是否存在网站/其它受众；缺合法 depth 仅暂停正式 Task/计划，普通分析/报告保存不受此门禁阻断。
- `DOC01`：读者是初次安装者，目标是完成当前真实受支持的首次启动；不是维护者的内部发布流程。
- `DOC02`：核实真实发布包和 CLI/安装方式。看不到目标运行版本时清晰记 `unverified`，不沿用历史 README 假定当前支持。
- `DOC03～05`：在明确文档写权后形成最小内容计划与差异、改 README；内部任务记录置于安全的仓库外目录。普通 README-only 没有网站时，G-DOC-04 的站点渲染/导航按 `N/A+reason`。
- `DOC06`：检查用户是否能找到第一步、示例是否对应实际包、内部审查内容是否泄漏；有计划和真实证据才写结论。
- `DOC07`：若有许可与环境可实际执行首次安装步骤并保存证据；无环境 `unverified`，不能称“用户首次成功”。
- `DOC08`：因为用户明确“不发布”，记录 `N/A+reason`，不 push/deploy。
- `DOC09`：交付 README diff、源事实与未验证范围，等待适用人类验收。`DOC10` 仅新事实变化时插入。

**反例**：为了让 README 里虚构的 CLI 命令正确运行，偷偷新增 CLI 功能；没有站点却创建网站；文档 build 绿便宣称真实新手操作通过。

## 语言边界正反例（虚构，未执行）

**英文持续上下文**：用户持续用英文讨论并明确启用本插件，未设置语言偏好，也未逐字指定报告语言；回复、预检查、确认及新过程正文/人类可读文件名延续英文。英文代码、工具输出或引文不构成切换依据；既有中文历史不追译，明确有效的局部内容约定只覆盖对应范围。反例是无有效中文约定却因插件固定兜底生成中文过程文档。

**中文解释，维护英文目标**：用户用中文要求修正已有英文README，项目有效约定及读者仍使用英文。解释、任务描述等新过程材料延续本例的中文任务上下文；只把README中获准修订的内容按原英文约定写好，代码/命令保持技术字面量。反例是因为会话中文就把README整篇翻成中文，或因为目标英文就把全部过程记录强制英文。若用户明确改变目标文档语言，先核其准确范围与有效约定，不从本例推断。

**局部英文与短答**：用户明确“这段发布说明用英文”，只对该段应用；随后回复`yes`、贴英文代码或英文引文，不自动切换整个任务的语言，也不写入长期偏好。反例是据短答永久改英文、自动双语或翻译旧记录。仍按[偏好与文件命名](../references/文件目录版本与跨会话恢复.md#偏好与文件命名req-023)的有效优先级、作用范围与保存门禁处理；本例不是任何真实语言偏好批准事件。

**明确语言问题的肯定短答**：助手只问“是否把本任务后续答复与过程正文改为英文？”，用户下一轮真实回复`yes`。此时yes指向唯一语言决定，后续答复与新过程正文按本任务范围用英文；不是无上下文的普通短答，也不永久保存偏好、追译历史或授予文件写权。反例是只因回复字面为yes便要求再次选择；若多个未决事项导致指向不明，仍先消歧。此例为虚构教学，不是实际验收证据。
